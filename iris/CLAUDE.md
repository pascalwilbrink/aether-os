## Iris

Iris is the web frontend for Aether-os (see `../CLAUDE.md`): a Next.js 16 app (App Router, React 19, TypeScript, Tailwind CSS v4, ESLint, Cache Components on) in the pnpm workspace (run `pnpm install` from `../`). Read `AGENTS.md` first: this Next.js differs from older versions (e.g. `proxy.ts` replaces middleware), and its guides are in `node_modules/next/dist/docs/`.

```bash
pnpm dev            # dev server (Turbopack) on :3000
pnpm build          # also checks prerendering (session reads must sit behind <Suspense>)
pnpm lint
pnpm test           # vitest: lib/**/*.test.ts
pnpm generate:api   # lib/api/generated from @aether-os/contracts (Hephaestus, Polis, Pistis, Proxenos, Kairos, Kerykes, Loculus, Agora, Pylon and Seshat specs)
```

Locally Iris needs Pistis, Polis, Hephaestus, Agora and Pylon running (`localhost:3003` / `3001` / `3002` / `3008` / `3011`), Proxenos (`3004`) for GitHub, Kairos (`3005`) for automations, Kerykes (`3006`) for the inbox and Seshat (`3009`) for knowledge; without them the GitHub page, the project's repositories, its automations, its knowledge and the inbox say they're unavailable (the inbox link drops its count) and the rest works. Configuration is read on the server when used (`lib/config.ts`): `PISTIS_ISSUER`, `IRIS_CLIENT_ID` (`iris`), `IRIS_URL`, `IRIS_SESSION_SECRET` (≥ 32 characters), `POLIS_URL`, `HEPHAESTUS_URL`, `AGORA_URL`, `PYLON_URL`, `SESHAT_URL`, `PROXENOS_URL`, `KAIROS_URL`, `KERYKES_URL`, `PISTIS_URL` (Pistis's API; defaults to the issuer's origin); outside production each has a local default, `next start` (production) needs them all (`.env.example`). To sign in locally, create a user with Pistis's `operator` development client (`../pistis/CLAUDE.md`, "Creating a user locally").

## Signing in (`lib/auth`, `app/auth`, `proxy.ts`)

Iris is Pistis's OAuth client on the server ("backend for frontend"): the browser never holds a token.

- **Flow:** `GET /auth/sign-in[?organization=<id>][&returnTo=/path]` starts an authorization code flow with PKCE, `state` and `nonce` (`openid-client`) as the public client `iris`, scope `openid profile email api offline_access`, `prompt=consent` (for a refresh token; Pistis grants it without a page), and the resource `urn:aether-os` or `urn:aether-os:org:<id>`. The pending sign-in is kept in a short-lived encrypted cookie (`iris_sign_in`, 10 minutes). `GET /auth/callback` checks it, redeems the code and stores the session; an `error` (e.g. `access_denied` for an organization the person can't enter) goes back to `/orgs?error=…`.
- **Session:** `lib/auth/session.ts`, an encrypted `httpOnly`, `SameSite=Lax` cookie (`iris_session`, a JWE: `dir` + `A256GCM`, key from `IRIS_SESSION_SECRET`; `secure` in production) holding the user (`sub`, name, email), the organization, the access, refresh and ID tokens. Read it with `currentSession()` / `requireSession()` (`lib/auth/current.ts`) inside a `<Suspense>` boundary.
- **One organization at a time:** a token is for one organization (`docs/identity.md`), so choosing another (`/orgs`, or opening `/orgs/<id>` with another organization's session) is a new sign-in for that resource. With Pistis's session there it's a redirect round trip without a page.
- **Refreshing:** `proxy.ts` refreshes the access token a minute before it expires (Server Components can't set cookies, and Pistis rotates refresh tokens, so the new ones must be stored before rendering), on this request and in the browser. If refreshing fails (expired, membership revoked) the session is dropped and pages send people to sign in. If Pistis doesn't answer (`isRefusal` is false and its `/health/live` doesn't answer), the session is kept: with its access token still valid the page renders, else `proxy.ts` rewrites to `/unavailable`, which waits for the services and reloads the page. Signing in, the callback and signing out say "Pistis can't be reached" (`?error=pistis-unavailable`) instead of failing, and sign-out still leaves Iris.
- **A refused token:** when a service answers `401` ("The token is invalid or expired": Pistis's keys changed, as on every local Pistis restart without `PISTIS_SIGNING_KEYS`, or the session was revoked), `call()` (`lib/api/http.ts`) redirects to `GET /auth/expired?token=<fingerprint>`, which drops the session and lands on the home page with "Your session expired". Only a session holding that token (`tokenFingerprint`) is dropped, so a link from elsewhere can't sign people out. Code that catches API errors must let the redirect through: `messageOf` rethrows it, elsewhere call `unstable_rethrow` first (`orUnavailable`, the sidebar's `settled`, the inbox).
- **Sign-out:** a `POST /auth/sign-out` form (a cross-site POST doesn't carry the `Lax` cookie) clears the session and sends people to Pistis's RP-initiated logout, which asks to confirm and comes back to `/`.
- **Server Functions** (`app/orgs/actions.ts`, `app/orgs/[organizationId]/agents/actions.ts`, `app/orgs/[organizationId]/councils/actions.ts`, `app/orgs/[organizationId]/members/actions.ts`, `app/orgs/[organizationId]/github/actions.ts`, `app/orgs/[organizationId]/budget/actions.ts`, `app/orgs/[organizationId]/model-keys/actions.ts`, `app/orgs/[organizationId]/tool-servers/actions.ts`, `app/orgs/[organizationId]/skills/actions.ts`, `app/orgs/[organizationId]/projects/[projectId]/actions.ts`, `app/orgs/[organizationId]/projects/[projectId]/automations/actions.ts`, `app/orgs/[organizationId]/notifications/actions.ts`, `app/orgs/[organizationId]/projects/actions.ts`, `app/orgs/[organizationId]/projects/[projectId]/knowledge/actions.ts`, `app/orgs/[organizationId]/projects/[projectId]/copilot/actions.ts`) check the session themselves: they're endpoints of their own. A refused form returns what was submitted (`values`, from `lib/forms.ts`) and the form starts from it, since React resets a form after its action; a `<select>` is keyed on its default as well, because a reset doesn't move it to a new one. Errors become messages with `messageOf` (`lib/api/messages.ts`: by problem `code`, then status). Pages under an organization call `requireOrganization(id, returnTo)`, which signs in again for that organization when the session is for another one.

- `…/knowledge` (`../docs/knowledge.md`, Seshat): search by words and meaning (`?q=`, proposals included; each result's kind, status, how it matched and its passage; "words only" when meaning isn't available), the proposals waiting for review with **Accept** and **Reject**, every item filtered by kind and status (`?type=`, `?status=`), **From repositories** (each of the project's repository links from Proxenos, with how Seshat indexes it: status, documents, skipped files, the commit and when it was read, the error; **Read again**, **Stop indexing** after a confirmation, and its paths, one per line, `RepositoryPathsForm`; a link that isn't indexed offers **Index documents** with the default paths; `pathsFromText` in `lib/knowledge.ts`), and forms to **write something down** (a decision, convention, fact, architecture note or lesson: kind, title, Markdown body, tags; a person's is accepted at once) and to **add a document** (uploaded to Loculus with the person's token, then registered with Seshat, which indexes it; at most 10 MB; PDF and Word `.docx` are searchable by their text too). `…/knowledge/[itemId]`: the item (kind, status, version, who wrote or proposed it and from which task or repository, tags, what it supersedes or is superseded by), its body or, for a document, its file (download from Loculus, or for a repository's document the file on GitHub at its commit, with a note that it changes with a commit) and first passages, its versions (each expandable; a repository document's with its path and commit), Accept / Reject / Retire as its status allows (none for a repository's document), and for a written item a form for its next version. Linked from the project page. No role check in Iris: Seshat refuses (`knowledge:write`, `knowledge:approve`) and the form says so (`knowledge/actions.ts`).
- `…/templates/new`: a new template of the project (the same form, with what it extends and the project's knowledge). `…/templates/[templateId]`: a template's latest version (its effective content, with the knowledge it pins, each linked to its item and flagged when it isn't an accepted item of the project) and a form for a task from it, one field per declared input (the same service accounts and repositories as the new-task form, and knowledge to pin on top of the template's), and for the project's own template **Archive** and the form for its next version (an organization template links to its page instead).

## When services aren't up

The services start in any order (`pnpm start:dev`), so Iris expects some not to answer yet:

- `call()` (`lib/api/http.ts`) turns no answer (refused, timed out) and `502`–`504` into an `ApiError` with status `503` and `SERVICE_UNAVAILABLE` (`isUnavailable`), naming the service (`lib/services.ts`, `serviceNameFor`) unless it said more itself. Forms show it as their message (`messageOf`), `orUnavailable` lists show "unavailable".
- A page that throws anyway gets an error boundary (`app/error.tsx`, `app/orgs/[organizationId]/error.tsx` inside the layout so the sidebar stays, `app/global-error.tsx`), all `Recovering` (`app/components/recovering.tsx`): it reads Iris's `/health`, names the services that don't answer, and tries the page again (`retry`) by itself once they all do. Three failures in a minute with every service up (`lib/recovery.ts`, tested) is a real error: it says so, with the error's reference (and its message in development), and waits for **Try again now**.

## Health

`GET /health/live` (Iris runs) and `GET /health` (`app/health/`): whether each service Iris calls runs (its `/health/live`, 3 s), in the services' format (`../docs/engineering.md`, Health checks; `lib/health.ts`, `summarize`, tested): `down` (`503`) without Pistis, since nobody can sign in, `degraded` when another service is down. Outside `proxy.ts`'s session handling (no cookie, nothing refreshed).

## APIs

`lib/api/polis.ts`, `lib/api/hephaestus.ts`, `lib/api/pistis.ts` and `lib/api/proxenos.ts` call the services on the server with the session's access token (`lib/api/http.ts`: JSON, extra headers such as `idempotency-key`, problem details as `ApiError` with `status` and `code`). `lib/api/agora.ts`, Agora: agents and their versions (create, publish, archive), skills and their versions (list, read, create, archive), councils and their versions (list, read, create, publish, archive); `lib/api/pylon.ts`, Pylon: the model catalogue, model keys (the organization's and an agent's: list, set, remove; an Ollama server's models) and budgets (the organization's, a project's, an agent's); Hephaestus: tasks (and a task tree's budget, which it passes on to Pylon) (list, read, create, cancel, retry), executions, artifacts and their reviews, task templates and tasks from them; Polis: organization and project memberships (list, grant, change, remove); Pistis: the organization's people and its service accounts (create, disable, enable); Proxenos: connecting GitHub, installations (list, sync), repositories, and a project's repository links (list, link, unlink); `lib/api/kairos.ts`, Kairos: a project's automations (list, read, create, change, pause, resume, archive) and their runs; `lib/api/seshat.ts`, Seshat: a project's knowledge (list, read, versions, passages, write, change, accept, reject, retire, register a document, search) and the repositories whose documents it indexes (list, set paths, read again, stop); `lib/api/kerykes.ts`, Kerykes: the person's inbox (list, unread count, mark read or unread, mark all read). Proxenos's and Kairos's lists on shared pages go through `orUnavailable` (`lib/api/http.ts`): the service down, or no GitHub App configured (`503`), is shown as unavailable instead of failing the page.
