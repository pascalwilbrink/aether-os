# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Hephaestus is the Aether-os service that runs agents (see `../CLAUDE.md`). It keeps a **copy of Agora's agents** and their published, immutable **versions** (instructions, model, tools, skills, runtime), from Agora's events, to pin on tasks and run; it holds **workspaces**: sandboxed execution environments in a project, driven by user actions and provisioner callbacks, **tasks**: the work an agent does (`../docs/tasks.md`), with their lifecycle, the **runner** that executes them (`libs/runner`), running agents with Mastra, their model calls going through **Pylon**, the model gateway (`libs/models` is its client). Executions that need a sandbox get a hardened Docker container, recorded as a workspace, with shell tools for the agent; what agents produce are **artifacts** (`libs/artifacts`); tasks can come from **task templates** (`libs/templates`); agent versions take tools from the organization's **tool servers** (MCP, `libs/tools`) and pin versions of its **skills**, which Hephaestus keeps a copy of from Agora's events (`libs/skills`). Organizations and projects belong to **Polis**: Hephaestus keeps only their status (`libs/tenancy`), from Polis's events, and asks Polis's API about one it hasn't seen yet.

Target role: Hephaestus is the task runner. Agents and skills are Agora's (`../agora`, `../docs/skills.md`); the runner gets [Mastra](https://mastra.ai) as its agent runtime and sandbox layer, behind the ports it already has (`AgentRuntime`, `SandboxProvisioner`).

It follows `../docs/engineering.md` like Polis: NestJS 12 (ESM, TypeScript 6), controller → service → TypeORM repository with mappers, Zod DTOs generated from the spec, `typeorm-transactional`, Postgres with migrations, tests against Postgres in containers.

## Commands

```bash
pnpm install                   # from the workspace root (../)
cp .env.example .env           # once; then `docker compose up -d` in ../ for Postgres
pnpm start:dev                 # build, run migrations, then watch mode on $PORT (default 3002)
pnpm build
pnpm lint                      # oxlint --type-aware; no-floating-promises is an error
pnpm format                    # prettier (single quotes, trailing commas)
pnpm generate:api              # regenerate libs/core/src/api/generated from ../contracts/hephaestus.openapi.yaml

pnpm migration:run             # apply pending migrations (on dist/: build first)
pnpm migration:show
pnpm build && pnpm migration:generate src/database/migrations/<Name>   # then review it and add it to migrations/index.ts

pnpm test                      # unit tests (libs/**/*.spec.ts): transition tables, mappers, config; no database
pnpm test:e2e                  # integration (libs/**/*.int-spec.ts) and e2e (test/*.e2e-spec.ts) against Postgres; needs Docker
pnpm test libs/workspaces/src/workspace-transitions.spec.ts   # single file
pnpm test:e2e -t "publishes"   # filter by test name
```

## Configuration

Environment variables, validated at startup with the Zod schema in `libs/core/src/config/env.ts` (`hephaestusConfigModule()`, through Krepis's `validateEnv`): `DATABASE_URL` (required, Postgres), `POLIS_URL` (required, Polis's API), `RABBITMQ_URL` (required; Polis's events), `PISTIS_ISSUER` (required: whose tokens to trust), `PISTIS_JWKS` (optional: trusted keys instead, tests), `PISTIS_CLIENT_ID` (`hephaestus`) and `PISTIS_CLIENT_SECRET` (required: Hephaestus's own client at Pistis, for its calls to Polis), `OUTBOX_RELAY_INTERVAL_MS` (1000), `PORT` (3002), `NODE_ENV`. The runner: `AGENT_RUNTIME` (`none`, the default, starts no runner; `mastra` runs agents; `echo` finishes every task at once without a model, for local development), `RUNNER_POLL_INTERVAL_MS` (1000), `RUNNER_MAX_EXECUTIONS` (4 per instance), `RUNNER_MAX_TASKS_PER_ORGANIZATION` (10) and `RUNNER_MAX_TASKS_PER_PROJECT` (5), `RUNNER_PROVISIONING_TIMEOUT_MS` (10 minutes), `RUNNER_RUN_TIMEOUT_MS` (60 minutes), `RUNNER_HEARTBEAT_INTERVAL_MS` (15 s), `RUNNER_HEARTBEAT_TIMEOUT_MS` (2 minutes), `RUNNER_STOP_GRACE_MS` (30 s), `RUNNER_MAX_INFRASTRUCTURE_FAILURES` (3) and `RUNNER_RETRY_BACKOFF_MS` (10 s, doubled per retry), `REVIEW_MAX_ROUNDS` (3), `VERIFICATION_MAX_ROUNDS` (3). Sessions: `SESSION_IDLE_TIMEOUT_MS` (30 minutes without a run ends one), `SESSION_RUN_TIMEOUT_MS` (10 minutes per run, at most 14), `SESSION_REAPER_INTERVAL_MS` (60 s; 0 turns it off, as the tests do). `PYLON_URL` (required): Pylon, the model gateway (Models through Pylon, below). OpenBao, for tool servers' credentials: `OPENBAO_ADDR`, `OPENBAO_TOKEN`, `OPENBAO_KV_MOUNT` (`secret`). Sandboxes: `SANDBOX_DRIVER` (`none`, the default: versions that need a sandbox fail; `docker`: the local Docker engine, `DOCKER_HOST` or its socket), `SANDBOX_IMAGE` (`node:22-slim`; needs `sh`, and `git` for tasks that work in a repository), `SANDBOX_USER` (`1000:1000`; never root), `SANDBOX_CPUS` (1), `SANDBOX_MEMORY_MB` (2048), `SANDBOX_PIDS_LIMIT` (256), `SANDBOX_WORKSPACE_MB` (1024), and for `restricted` network access `SANDBOX_ALLOWED_HOSTS` (comma-separated, `*.` for subdomains; default the npm, PyPI, Go, crates.io, Maven and RubyGems registries), `SANDBOX_PROXY_IMAGE` (`node:22-alpine`) and `SANDBOX_EGRESS_NETWORK` (`bridge`). Tool servers: `TOOL_SERVER_ALLOW_PRIVATE` (false: whether Hephaestus may connect to private, loopback and link-local addresses and over `http://`; true in `.env.example` and tests), `TOOL_SERVER_TRUSTED_ORIGINS` (comma-separated origins that may be sent a task's own token: Aether-os's own servers, such as Seshat), `TOOL_CALL_TIMEOUT_MS` (60 s, per call and for connecting). Repositories: `PROXENOS_URL` (Proxenos's API, for repository tokens; without it tasks that work in a repository fail). Files: `LOCULUS_URL` (Loculus's API, where files agents submit are kept; without it agents have no `submit_file`), `TASK_FILE_MAX_BYTES` (25 MiB: an input file, or a file an agent submits). Knowledge: `SESHAT_URL` (Seshat's API; without it agents have no knowledge tools). Locally they come from `.env` (gitignored; `.env.example` has the defaults for `docker compose`).

## Running agents locally

`AGENT_RUNTIME=mastra` in `.env`, with Pylon running (`../pylon`, `PYLON_URL`), then set the organization's provider key in Iris (the organization's **Model keys** page, which calls Pylon; `../pylon/CLAUDE.md`).

An agent version's model is then `{ "provider": "anthropic", "model": "<model>" }`, a model of Pylon's catalogue (Agora checks it). The task's service account needs a role in the task's project with `model:invoke` (`editor` and above; Pistis's task token). For an agent that works in a shell, set `runtime.sandboxRequired` on its version and `SANDBOX_DRIVER=docker` (and `runtime.networkAccess: restricted` for one that installs packages): each execution then gets its own container (`docker ps --filter label=aether-os.sandbox=true`).

## Database

- **Postgres**, Hephaestus's own database (`hephaestus` in `../docker-compose.yml`), connected in `libs/core/src/database/database.module.ts` with Krepis's `postgresOptions` and `createTransactionalDataSource`.
- **Migrations only:** `src/database/migrations/` (registered in `migrations/index.ts`, oldest first), run by `pnpm migration:run` as a separate step, never at startup. The TypeORM CLI uses `src/database/data-source.ts` (compiled to `dist/`); list new entities there and in `test/global-setup.ts`. No down migrations: keep them compatible with the previous release.
- **Columns:** `uuid` IDs, `timestamptz`, `text`, enums as `text` with a check constraint, configuration objects as `jsonb`, and an index matching each keyset pagination.
- **Tests** run against Postgres 17.5 and RabbitMQ 4.1 in containers started once per `test:e2e` run (`test/global-setup.ts`): it applies the migrations and fails if the entities differ from the migrated schema. Files run one at a time; every test starts from emptied tables (`test/database.ts`). Tokens come from the run's `TestTokens` (`test/tokens.ts`, trusted through `PISTIS_JWKS` in `test/setup.ts`; `asMember` in `test/auth.ts`); integration tests use `actingAs(service, testPrincipal(...))`. Test apps replace `PolisClient` with `test/fake-polis.ts` (organizations and projects as Polis would return them) and deliver Polis's events through the real inbox (`deliverPolisEvent`, `organizationEvent`, `projectArchived`); `test/polis-events.e2e-spec.ts` goes through RabbitMQ. Agents come from Agora's events the same way (`test/agora.ts`: `publishedAgent`, `createAgent`, `publishVersion`, `archiveAgent`; `test/agents.e2e-spec.ts` goes through RabbitMQ).

## Architecture

`src/` is the app shell: `main.ts` starts telemetry (Krepis's `startTelemetry`, awaited) and then imports `server.ts`, which calls Krepis's `initializeTransactions()` before Nest boots and `configureHttpApp(app)` (the `/v1` prefix, Zod validation, the response serializer, problem details); `app.module.ts` imports the config, database and feature modules. Code lives in Nest libraries under `libs/`, registered in `nest-cli.json` and aliased in `tsconfig.json` as `@hephaestus/<name>`.

Dependency graph: `core` ← `tenancy` ← `agents`, `workspaces`; `tenancy`, `agents` ← `tasks` ← `artifacts`; `core`, `tenancy` ← `tools` ← `agents`; `core` ← `skills`; `core`, `tenancy` ← `models` ← `tasks`; `tasks`, `artifacts`, `models`, `tools`, `skills`, `workspaces` ← `runner`; `agents`, `tasks`, `tenancy` ← `templates`; `agents`, `tenancy`, `models`, `tools`, `skills`, `runner` ← `sessions`. The runner reaches Proxenos with the generated client (`libs/core/src/clients/proxenos`, `ProxenosApi`). A library's `index.ts` exports its module, services and errors, never entities, mappers or repositories.

Each feature library has the layout described in `../polis/CLAUDE.md`: `*.module.ts`, `*.controller.ts` (routes only), `*.service.ts` (rules, `@Transactional()`, tenancy; returns response DTOs), `*.entity.ts`, `*.mapper.ts` (UUIDv7 IDs), `*-transitions.ts` (the lifecycle as a pure table, tested exhaustively), `*.errors.ts` and one-line `createZodDto` classes in `dto/`.

- **Tenancy (`libs/tenancy`):** `OrganizationsService.assertExists` (reads: 404) and `assertAcceptsWrites` (writes: 404 or `ORGANIZATION_SUSPENDED`); workspaces are created through `ProjectsService.assertAcceptsWrites` (also `PROJECT_ARCHIVED`, and 404 for another organization's project). They read `organization_states` / `project_states`, Hephaestus's copy of Polis's state:
  - kept from Polis's events (`organization.created` / `.suspended` / `.reactivated`, `project.created` / `.archived`), consumed through Krepis's `EventsModule` subscription in `app.module.ts` (`POLIS_SUBSCRIPTIONS`; queue `hephaestus.polis-events`, inbox, retries, dead-lettering) and handled with `@OnDomainEvent('polis.<eventType>')`;
  - on a miss, fetched once from Polis's API through `PolisClient` (`HttpPolisClient`: the client generated from Polis's spec, 5 s timeout, one retry), which also covers organizations created before Hephaestus subscribed. Polis unreachable then is `503 UNAVAILABLE`;
  - every write is version-guarded (`aggregateVersion` for events, Polis's `version` for fetches): a late, repeated or older event never moves a state backwards.
  Everything is looked up within its organization, so another organization's resource is a 404.
- **Access** (`../docs/identity.md`, Krepis `AuthModule` in `app.module.ts`; `x-permission` in the spec): `createdBy` is the caller's `sub`. Workspace routes need an organization token (`org:read`), and `WorkspacesService` checks the project permission once the project is known: `workspace:read` to read, `workspace:manage` to create (the body's project) and for user actions; lists hold only workspaces in projects the caller can read; provisioner callbacks have no caller and no check.
- **Calling Polis:** `HttpPolisClient` sends Hephaestus's own token (`ServiceTokens`: `ClientCredentialsServiceTokens` with `PISTIS_CLIENT_ID` / `PISTIS_CLIENT_SECRET`, scope `platform:read`); no token from Pistis is `503 UNAVAILABLE`, like Polis being down.
- **Agora's check (`AgentVersionChecks`, `AgentVersionChecksController` in `libs/agents`):** `POST /v1/organizations/{id}/agent-version-checks` (`@PlatformAccess('platform:read')`: platform services only, for Agora with its own token) answers whether a version's tools (`TOOL_SERVER_INVALID`) can be chosen in the organization (its model Agora checks with Pylon's catalogue, its skills itself), with `204` or the same `409` creating a version gets; it changes nothing. Hephaestus owns what it checks, so Agora asks before it creates a version (one-way: Hephaestus never calls Agora).
- **Councils (`libs/councils`): a copy of Agora's** (`../docs/councils.md`), from `agora.events` (`council.created`, `council.archived`, `council-version.published`, `council-version.deprecated`), guarded by the council's `version` like agents (a council the copy doesn't have yet throws, `CouncilNotCopiedYetError`, so the consumer retries). Versions are stored whole (`content`, the type of `council-version.published`'s `version`). `CouncilsService.publishedVersion` (404, `COUNCIL_UNAVAILABLE` when archived or unpublished) is for council sessions, still to come; there's no council API yet.
- **Sessions (`libs/sessions`, `../docs/interaction.md`):** a person's conversation with an agent in a project, over AG-UI. `/v1/organizations/{organizationId}/projects/{projectId}/sessions`: create (`session:use`; a user's own token only, else 403; the project must accept writes; the agent's published version is pinned like a task's), list (the caller's, newest first, `?status=`), read, `…/messages` (oldest first), `…/end` (`closed`, idle tolerated), all `session:use` and only for the person who started it (`startedBy`; anyone else's is a 404). `sessions` (`runningSince` is the run lock, `lastActivityAt`, `endedReason`, `version` for events) and `session_messages` (`ordinal` and the AG-UI `messageId` unique per session; `role` `user` / `assistant` / `tool`, `content`, `toolCalls` jsonb, `toolCallId`, `toolName`; migration `Sessions`).
  - **Runs** (`POST …/{sessionId}/runs`, `SessionsController.run`, `SessionRunsService`): the body is AG-UI's `RunAgentInput` (`threadId` must be the session's ID). `SessionsService.startRun` locks the session row, refuses an ended session (`SESSION_ENDED`) or one running for less than `SESSION_RUN_TIMEOUT_MS` (`SESSION_BUSY`), adds the input's new messages (`newMessages`: unknown `user` messages, and `tool` messages answering one of the agent's calls, once; everything else is the frontend's copy, ignored; none is a 400), and sets `runningSince`. Then a session token (`SessionTokens` → `PistisSessionTokens`: token exchange of the caller's own bearer token, `subject_token_type` access token, with `project_id`, `session_id`, `agent_id`, `agent_version_id`, 900 s; Pistis refusing is a 403, not answering a 503; the lock is released). Only then the stream starts (`text/event-stream`, `data: <event>` frames, `agui.ts`).
  - **The turn** (`SessionAgent`, `session-agent.ts`): a Mastra `Agent` from the pinned version (its instructions plus `sessionInstructions`, the model from `ModelGateway.resolveForSession` with the session token, no execution header; the version's tool servers connected with the session token; its skills through `InMemorySkillSource`; the knowledge tools without `propose_knowledge`), streamed with `agent.stream` (20 steps, the version's temperature and max tokens, `maxRetries: 0`) on the session's history (`modelMessages`: AI SDK messages; a tool call never answered gets a "no answer" result) after a system message with the input's `context` and `state`. The input's `tools` are Mastra `clientTools` (schemas from JSON Schema, `z.fromJSONSchema`, no `execute`): calling one ends the turn. `TurnWriter` maps `fullStream` chunks to AG-UI events (`text-delta` → `TEXT_MESSAGE_*`, `tool-call` → `TOOL_CALL_START`/`ARGS`/`END`, `tool-result` / `tool-error` → `TOOL_CALL_RESULT`) and collects the produced messages; then `RUN_FINISHED`, or `RUN_ERROR` with a code (`failureOf`: Pylon's `402 BUDGET_EXHAUSTED`, `MODEL_FAILED`, `TOOL_SERVER_UNAVAILABLE`, `SKILL_UNAVAILABLE`, `RUN_TIMEOUT` after `SESSION_RUN_TIMEOUT_MS`, `RUN_STOPPED` when the client went away, `AGENT_FAILED`). `finishRun` always keeps what was produced and releases the lock.
  - **Idle sessions:** `SessionReaper` ends sessions without a run for `SESSION_IDLE_TIMEOUT_MS` (`idle`; `SessionsService.endIdle`, batches `FOR UPDATE SKIP LOCKED`; a lost run doesn't keep one).
  - **Events:** `session.started` and `session.ended` (`reason`) in the change's transaction.
  - Tests: `test/sessions.e2e-spec.ts` (streams through supertest; `FakeSessionTokens` in `test/fake-session-tokens.ts`, `ScriptedPylonModels.doStream`, `FakeKnowledgeBase`, all from `createApp`), `session-messages.spec.ts`.
- **Agents and versions (`libs/agents`): a copy of Agora's.** Agora owns them (`../agora`); Hephaestus serves no agent API. It consumes `agora.events` (`AGORA_SUBSCRIPTIONS` in `app.module.ts`; queue `hephaestus.agora-events`, inbox, retries) with `@OnDomainEvent('agora.<eventType>')` in `AgentsService`: `agent.created` inserts the agent (once), `agent.archived` archives it, `agent-version.published` stores the whole version (`AgentVersionsService.store`; versions never change) and makes it the agent's `latestVersionId`, `agent-version.deprecated` marks one deprecated (it stays runnable for the tasks that pinned it). Each agent records the last event applied (`version`, the events' `aggregateVersion`): an event that isn't newer changes nothing about the agent (a late `published` still stores its version, as deprecated), and an event about an agent the copy doesn't have yet throws (`AgentNotCopiedYetError`), so the consumer retries it after `agent.created`. Tasks pin the agent's published version from the copy (`AgentsService.publishedVersion`: 404, `AGENT_ARCHIVED`, `AGENT_NOT_PUBLISHED`), so a version Agora just published can be used once its event is in (normally within a second); the runner reads it with `AgentVersionsService.findById`, as an `AgentVersion` (the type of `agent-version.published`'s `version`, `@hephaestus/core`). Rows from before Agora are version 1 (migration `AgentsFromAgora`), as Agora's import starts them.
- **Workspaces:** `workspace-transitions.ts` lists every allowed (status, action) pair; anything else is `WORKSPACE_INVALID_TRANSITION`. Workspace transitions are strict, not idempotent. User actions (acquire, release, suspend, resume) need an active organization; destroy only an existing one (a suspended organization can still release resources); provisioner callbacks (`startProvisioning`, `markReady`, `markDestroyed`, `markFailed`, `expire`, service methods without HTTP routes) skip the check, as do the runner's own (`createForExecution`, `acquireForExecution`, `destroyForExecution`). `repository` is optional (an execution's sandbox has none yet). `expiresAt` must be in the future (`WORKSPACE_INVALID_EXPIRY`).
- **Tasks (`libs/tasks`, `../docs/tasks.md`):** `/v1/organizations/{organizationId}/projects/{projectId}/tasks`: create (`task:create`), list (by `parentTaskId`, `status`) and read (`task:read`), `cancel` (`task:cancel`) and `retry` (`task:create`), all in the route's project (Krepis: no role there is a 404).
  - **Creating** needs an `Idempotency-Key` header: the same key in the organization returns the task it created (`200`) instead of a second one (also when two requests race: the unique constraint decides). The agent's published version is pinned (`AgentsService.publishedVersion`: `AGENT_NOT_PUBLISHED`, `AGENT_ARCHIVED`), the project must accept writes, `review.artifactKinds` (kinds whose artifacts need approval, `*` for all) and `acceptanceCriteria` (unique `key`s, else `TASK_CRITERIA_INVALID`; `source: task`) are pinned on it, and the task runs as `serviceAccountId` (a Pistis service account; tasks never run as a user) with the caller recorded as `requestedBy`.
  - **Concurrency keys** (`../docs/tasks.md` Concurrency): `concurrency: { key, policy }` on a top-level task (`TASK_CONCURRENCY_INVALID` on a subtask; also from templates and commands), stored as `concurrency_key` / `concurrency_policy`. `TasksService.create` takes an advisory lock on the project and key for the transaction, then looks for unfinished tasks of the project with that key: `skip` refuses (`TASK_CONCURRENCY_SKIPPED`), `cancel-previous` cancels them (as `cancel` does, subtrees too), `queue` creates it anyway, and `TaskQueue.claimNext` skips a queued task while an older unfinished one (by `created_at`, `id`) has its key.
  - **Input files** (`../docs/files.md`): `inputFiles: [{ fileId }]` (at most 20, duplicates dropped), files of the task's project in Loculus, stored as `input_file_ids`; not checked when created (the task token reads them when it runs). `TaskInputs` (`ExecutionPreparer.inputFiles`, after the checkout): each through `FileStore.fetch` (Loculus's file, available, at most `TASK_FILE_MAX_BYTES`, its download checked against the recorded SHA-256), written to `/workspace/inputs/<name>` through `exec` stdin (names kept apart: `brief-2.md`); the runtime gets them as `inputFiles` and the Mastra prompt lists them as data (`withInputs`). A version without a sandbox, or a file gone, pending or too large, fails the execution without retrying; Loculus or the storage not answering is retried (`FileStoreError.retryable`).
  - **The brief** (`../docs/tasks.md` Task fields; `task-fields.ts`, `taskBriefOf`, pure, unit-tested): `description` (stored in the `instructions` column; the request's `instructions` is its old name, accepted when `description` is absent, and the response returns both), `requirements` and `constraints` (`{ key, description }`, at most 50 each, keys unique across both), `expectedOutcome`, and `deliverables` (`{ key, kind: text | json | file | pull_request, description, primary?, path? }`, at most 20, keys unique, one primary at most, `path` only on a file, a `pull_request` one only with a repository, its own or its parent's), checked in `TasksService.create` (`TASK_FIELDS_INVALID`; a criterion's `requirementKey` must name a requirement or constraint, `TASK_CRITERIA_INVALID`). Each deliverable adds a criterion `deliverable.<key>` (`source: deliverable`, `{ type: artifact, deliverable }`) after the template's and the request's, keys unique across all. Migration `TaskFields`. Artifacts record `deliverableKey`: `ArtifactsService.record` refuses a key that isn't one of the task's deliverables, of another kind, or a file not matching its `path` (`matchesPath`, `*` for anything), and makes the primary deliverable's artifact primary; the agent sets it with `deliverable` on `submit_artifact` and `submit_file`, and the runner sets it on the `pull_request` artifact of a `pull_request` deliverable. `Verifier` passes a `deliverable` check when a non-partial, non-rejected artifact has its key, or for a `pull_request` deliverable when `git -C <repo> rev-list --count <baseSha>..HEAD` in the sandbox counts any commits (failing that command throws, never a pass). The Mastra prompt starts with `briefOf` (`task-brief.ts`): title, description, expected outcome, requirements, constraints, deliverables (and how to submit them), and the criteria (the deliverables' own left out). Templates carry the same fields (their `instructions` is the task's description, `description` being the template's own); a project template appends its description and expected outcome and adds requirements, constraints and deliverables (`TASK_TEMPLATE_INVALID` for a key twice or two primaries), and placeholders fill every text field (`render`). Tests: `task-fields.spec.ts`, `task-brief.spec.ts`, `verifier.spec.ts`, `template-content.spec.ts`, `test/tasks.e2e-spec.ts`, `verification.int-spec.ts`.
  - **Pinned knowledge** (`../docs/tasks.md` `context`, `../docs/knowledge.md` Pinned context): `context: [{ kind: 'knowledge', itemId }]` (at most 50, duplicates dropped). `TaskBudgetsService.create` (the HTTP API and `task.create` commands) pins them before creating the task, unless the idempotency key already made it: `TaskContextSource` (`task-context.ts`; `SeshatTaskContextSource` with `SESHAT_URL`, Seshat's `GET …/items/{id}` with Hephaestus's own token, `platform:read`, a refused token renewed once; `NoTaskContextSource` without, refusing any) takes only accepted items of the project (else `TASK_CONTEXT_INVALID`; Seshat or Pistis not answering is `503`) and keeps each as `PinnedKnowledge` (ID, version, type, title, a written item's body up to 32 KiB with `truncated`, a document's file name). The task stores the summary as `context` (in its API) and the whole as `context_content` (`select: false`, migration `TaskContext`); `TasksService.pinnedContext` reads it for the runner (`TaskInputs.context`, `ExecutionPreparer.context`), the runtime gets it as `context`, and the Mastra prompt puts written items in `<knowledge>` blocks as reference material and lists documents for `read_knowledge` (`withPinnedContext`, `knowledge-tools.ts`). Tasks from templates pin the template's (`context` in its content, only on a project's template since knowledge belongs to one project, else `TASK_TEMPLATE_INVALID`; each item once) and the request's (`TemplatedTasksService`, the same idempotency check). Tests: `task-context.spec.ts` (Seshat at a local server), `knowledge-tools.spec.ts`, `test/tasks.e2e-spec.ts` and `test/runner.e2e-spec.ts` with `FakeTaskContextSource` (`test/fake-knowledge.ts`, `knowledge` from `createApp`).
  - **Text from outside** (`../docs/git.md` Untrusted input; `untrusted-inputs.ts`): `untrustedInputs: [{ name, source, value }]` (at most 20, names unique, `TASK_FIELDS_INVALID`), stored as `untrusted_inputs` (migration `UntrustedInputs`), named `{{name}}` in the task's text fields, which are stored as given. The mapper fills them in (`fillUntrusted`), so the API and everything reading a task see the values; the runner gives the runtime the brief as given (`TasksService.briefForPrompt`, `TaskInputs.forPrompt`, only for a task with untrusted inputs), and `briefOf` puts each value in an `<untrusted-input name source>` block (a `</untrusted-input>` in it escaped), after a note naming where they came from and that they're data. Kairos sends the issue's title this way; a task from a template takes them too (`inputs` values can name them). Tests: `untrusted-inputs.spec.ts`, `task-brief.spec.ts`, `test/tasks.e2e-spec.ts`, `test/runner.e2e-spec.ts`, `test/templates.e2e-spec.ts`.
  - **Repository** (`../docs/git.md`): `repository: { linkId }` names one of the project's repository links in Proxenos (checked when the task runs, not when it's created); a subtask without one works in its parent's, since a task tree shares a branch. Tasks from templates take it from the request.
  - **Trees:** `parentTaskId` makes a subtask (not under a finished task: `TASK_PARENT_FINISHED`); every task records its `topLevelTaskId`. `dependsOn` may only name tasks under the same top-level task (`TASK_DEPENDENCY_INVALID`; a top-level task has none). A task starts `blocked` until all its dependencies have succeeded, else `queued`; when a task succeeds, its blocked dependents whose dependencies have all succeeded become `queued`.
  - **Lifecycle:** `task-transitions.ts`, every (status, action) pair of the lifecycle in `docs/tasks.md`, tested exhaustively; anything else is `TASK_INVALID_TRANSITION`. People `cancel` (the task and every unfinished task under it; idempotent; a suspended organization can still cancel) and `retry` (a failed task, same pinned inputs, `attempt` + 1, back to `queued` or `blocked`). The runner moves tasks with `TasksService.transition` (no HTTP route); `fail` needs a `failureReason`, `requeue` (an infrastructure failure retried) takes the backoff as `notBefore` (`nextAttemptAt`), `await-review` takes the drafts (`reviewRound` + 1, `task.awaiting-review`), `revise` (changes requested) queues it again.
  - **Events** (`../contracts/hephaestus.asyncapi.yaml`, `HephaestusEvents` in `@hephaestus/core`): `task.created`, `task.status-changed` (from, to, reason) on every change, and `task.succeeded` / `task.failed` / `task.cancelled`, in the change's transaction (outbox → `hephaestus.events`). `version` on a task is its events' `aggregateVersion`.
- **Runner (`libs/runner`, `../docs/tasks.md` Task lifecycle):** every instance runs one `TaskRunner` (when `AGENT_RUNTIME` isn't `none`), all on the same tables, so instances can come and go.
  - **Claiming** (`TaskQueue` in `libs/tasks`, through `ExecutionsService.claim`): a `queued` task whose backoff has passed, locked `FOR UPDATE SKIP LOCKED` (no two instances take the same task); the organization with the fewest running tasks first, then subtasks, then oldest; within `RUNNER_MAX_TASKS_PER_ORGANIZATION` / `_PER_PROJECT`, counted under a per-organization advisory lock; never in a suspended organization or archived project (those tasks wait). The claim moves the task to `provisioning` and records its **execution** in the same transaction.
  - **Executions** (`executions` table; `GET …/tasks/{taskId}/executions`, `task:read`): one per try, numbered within the task, with the task's `attempt`, `status` (`provisioning`, `running`, `completed`, `failed`, `cancelled`, `paused`), `failureReason`, `error`, `summary` (the agent's final answer), the sandbox reference, `heartbeatAt` and `deadlineAt`. At most one active per task (a partial unique index). Every change to an execution and its task's transition is one transaction, execution row locked first; an execution that already ended changes nothing (`ExecutionsService`). The list is `ExecutionHistory`: each with its usage, its `sandbox` and its `traceId`.
  - **Running one** (`TaskRunner.execute`): the pinned agent version, a task token (`TaskTokens` → `PistisTaskTokens`: token exchange as Hephaestus's own client; refused → `access_denied`, no retry; the token's `org_id` must be the task's organization), a sandbox if the version needs one (`SandboxProvisioner`, below), then `running` with the run deadline, then the `AgentRuntime` port (`AGENT_RUNTIME`: `MastraAgentRuntime`, or `EchoAgentRuntime`, which calls no model). Completed → `verifying` (Verification, below) → `delivering` → `succeeded` (nothing to deliver yet) with the execution's artifacts `final` and its primary artifact on the task (`primaryArtifactId`; without any outcome the task fails `agent_failed`), or, when some need approval, → `awaiting_review` with them as drafts (Reviews, below); the agent giving up → `agent_failed`. The runtime gets an `ArtifactSink` bound to the execution (`ExecutionsService.recordArtifact`, refused once the execution ended); a failed or cancelled execution's pending artifacts become `partial`. Whatever the execution left behind is destroyed, found by its execution ID (also when provisioning was abandoned).
  - **Failures** (`RunnerFailure` from the ports: a reason and whether retrying helps; anything else thrown is a retryable infrastructure failure): a retryable infrastructure failure requeues the task (`requeue`) with backoff while the attempt has had fewer than `RUNNER_MAX_INFRASTRUCTURE_FAILURES`, then fails it `infrastructure`; an execution interrupted by shutdown is requeued without counting.
  - **Stopping:** the runtime gets an `AbortSignal`, aborted at the run deadline (`timeout`), the provisioning timeout (infrastructure), a cancelled task (seen at the next heartbeat; the execution ends `cancelled`), a lost execution, or shutdown; after `RUNNER_STOP_GRACE_MS` it's abandoned.
  - **Activity** (`../docs/tasks.md` Activity): `execution_events` (`ExecutionEventEntity`: `sequence` per execution, `type` `log` / `model_call` / `tool_call`, `level`, `message`, `toolName`, `input`, `output`, `text`, tokens). `ExecutionsService.activityFor(executionId)` gives an `ExecutionActivity` (`execution-activity.ts`: `log`, `modelCall`, `toolCall`; writes one after another, never throws, at most 2,000 per execution; `activity-text.ts` shortens and redacts every text first); `ExecutionEventsService.append` numbers each event in the table (`MAX(sequence) + 1`, tried again on a unique violation). `TaskRunner` logs its steps and how the execution ended; the runtime gets it as `activity`, and the Mastra runtime records each step in `onStepFinish` (`step-activity.ts`, `recordStep`: the model call, then each tool call from the step's AI SDK content, `tool-result` outputs `{ type, value }` with `error-*` types as errors, or Mastra's `{ payload }` chunks). `GET …/executions/{executionId}/events?after=&limit=` (`task:read`, `ExecutionsController`): oldest first, `nextAfter`, the execution's status. Tests: `activity-text.spec.ts`, `step-activity.spec.ts`, the runtime's in `mastra-agent-runtime.int-spec.ts`, the route in `test/runner.e2e-spec.ts`.
  - **Heartbeats and the reaper:** each instance refreshes `heartbeatAt` of its executions; each poll, `ExecutionReaper` ends any instance's executions past the heartbeat or provisioning timeout (infrastructure, retried) or the run deadline (`timeout`), and destroys their sandboxes.

- **Repositories in sandboxes (`RepositoryCheckouts`, `../docs/git.md` Inside the sandbox):** for a task with a repository, after its sandbox is provisioned (within the provisioning timeout): the sandbox must have `git` (else the execution fails without retrying, as it does for a version without a sandbox); a **read** token comes from Proxenos (`RepositoryTokens` → `HttpRepositoryTokens`, the generated Proxenos client, with the **task's own token**; 403/404 → `access_denied`, 409 → infrastructure without retrying, otherwise retried); `GitClient` (the `git` CLI on Hephaestus's side, no user or system config, credentials only in `GIT_CONFIG_*` environment variables, never on the command line) clones it fully into a temporary directory, from the task tree's branch `aether/<topLevelTaskId>` if the remote has it (the work of finished dependencies) or else the default branch; and the clone goes into the sandbox as a git bundle through `docker exec` stdin (`SandboxDriver.exec`, bytes in and out: `docker cp` reaches neither tmpfs nor a read-only root). In the sandbox it is `/workspace/repo`, on the task branch, without a remote, committing as `Aether-os <aether-os@users.noreply.github.com>`, with a `commit-msg` hook adding `Aether-Task: <task ID>`; **the sandbox never sees a token and still has no network**. The execution records `repository` (link, `fullName`, `branch`, `baseSha`), the runtime gets `repository` (the Mastra prompt says where it is and that only commits are kept). When a run passes verification, before completing: the commits on top of the base come out as a bundle through `docker exec` stdout, are verified and fetched into Hephaestus's clone (`refs/aether/result`; bundles from sandboxes run with hooks and fsmonitor off) and must descend from the base (else `agent_failed`); the execution records `headSha`, `commits` and `uncommittedChanges` (not kept). Then **they're pushed** (`RepositoryCheckouts.push`, `../docs/git.md` Branches and pull requests): commits that change `.github/workflows` are refused (`agent_failed`; the app has no `workflows` permission anyway); a **write** token comes from Proxenos; only `aether/*` branches, **never forced**: if the branch moved since the checkout (a sibling subtask pushed) the commits are rebased onto it first (as the Aether-os committer), and a push that loses a race is tried again (3 times); a rebase conflict goes **back to the agent** (`BranchConflictError`, then `RepositoryCheckouts.startConflictResolution`): the branch's new commits go into the sandbox as a bundle (`refs/aether/upstream`), the agent's commits are rebased onto them there (`--autostash`), stopping at the conflicts; the checkout's base becomes the branch's head, the task goes back to `running` (`ExecutionsService.returnToAgent`, `reason: branch-conflict`), and the agent runs again with `conflict` (the branch and the conflicted files; the Mastra prompt says to resolve them and run `git rebase --continue`), is verified again, and its commits are collected and pushed again. A rebase left unfinished fails the execution `agent_failed`. Conflicts share the execution's `VERIFICATION_MAX_ROUNDS`; once they're used up, the execution fails as a retryable infrastructure failure and the next one starts from the branch's head. The execution records `pushedSha`, and the commits become a **`pull_request` artifact** (Hephaestus's own, `ArtifactsService.record` with `NewPullRequest`; never from the agent's tool): the task's title, the run's summary plus `Aether-Task` as the description, the branch, `baseBranch` (the default branch), `headSha` (the pushed head), `pullRequest: null` until delivery opens it; primary (the outcome of a coding task), revising the `pull_request` a reviewer sent back in a revision run, and a draft like any artifact when `review.artifactKinds` names `pull_request` (the branch is pushed already: a draft is the branch at its head). Nothing committed: nothing pushed, no `pull_request`. Hephaestus's clone is removed when the execution ends. Commits are made as the GitHub App's bot (`committer` from Proxenos's token response: `<slug>[bot]` and its noreply email), in the sandbox and when rebasing.
- **Delivery and branch cleanup (`Deliveries`, `../docs/git.md`):** a task whose final artifacts include a `pull_request` not opened yet stays `delivering` (from `ExecutionsService.complete` or an approval in `ReviewsService`) instead of succeeding at once. Each runner round (`TaskRunner.round`, before claiming tasks) delivers what's due: `TaskQueue.claimDelivery` takes a `delivering` task (`FOR UPDATE SKIP LOCKED`, `next_attempt_at` as a 5-minute lease, `delivery_attempts` counted), `TaskRepositoryAccess` gets a write token (a short task token, then Proxenos), and the `PullRequests` port (`GitHubPullRequests`, GitHub's REST API at Proxenos's `apiUrl`) opens each pull request, or adopts and updates the branch's open one (a `422` on creating), recording `pullRequest` (number, URL, state) on the artifact; then the task succeeds (`reason: delivered`, its latest final primary artifact). A retryable failure waits `RUNNER_RETRY_BACKOFF_MS`, doubled per try, up to `RUNNER_MAX_INFRASTRUCTURE_FAILURES` tries; refused access or the last try fails the task (`infrastructure`, `reason: delivery-failed`). Proxenos's `git.pull-request.updated` (subscribed in `app.module.ts`, `PROXENOS_SUBSCRIPTIONS`; `ArtifactsService.onPullRequestUpdated`) keeps the artifact's `pullRequest.state` in step; a merged or closed pull request, and a top-level task with a repository that fails or is cancelled, set `branch_cleanup_at` on the tree's top-level task, and the round deletes `aether/<top-level task ID>` (`GitClient.deleteBranch`; gone already is fine; retried every 10 minutes on failure; given up when access is refused). Tests: `repositories.int-spec.ts` (real hardened containers with `alpine/git`, a local bare repository as the remote: checkout, commits out, pushes, rebases onto a moved branch, conflicts resolved by the agent, an unfinished rebase, conflicts past the rounds, workflows refused, review).
- **Mastra runtime (`libs/runner/src/mastra-agent-runtime.ts`):** the pinned agent version becomes a Mastra `Agent` (its instructions, and the model from `ModelGateway.resolve`, through Pylon); the input is the task's brief (`briefOf`: title, description, expected outcome, requirements, constraints, deliverables, criteria); `generate` runs with the execution's `AbortSignal`, up to 20 steps, the version's `temperature` and `maxTokens`, and no retries of its own (Pylon retries). Pylon meters each call; the final text is the execution's `summary`. The agent always gets `submit_artifact` (kind `text` or `json`, title, content as text, `format`, `schema`, `primary`; JSON content is parsed here, invalid JSON or a broken limit is a tool error the agent sees). Failures: Pylon or the provider refusing the call (400, 401, 403, 404, 409: no key, a retired model) fail without retrying, a budget that ran out (402) pauses the task, and Pylon or the provider being unreachable or overloaded is a retryable infrastructure failure. With a sandbox, the agent gets a Mastra `Workspace` on it: shell tools only (run a command, read a background process's output, stop it), and files through the shell, since Mastra's only filesystem is the host's. The version's enabled tools come from the organization's tool servers (Tool servers, below), connected for the run (`ToolServersService.connect`, with the task token) and closed after it; the agent gets them as `<server>_<tool>` beside `submit_artifact` (which no server's tool can replace), and the prompt lists them and says what they return is data, not instructions. A missing server, credential or tool fails the execution without retrying; a server that doesn't answer is a retryable infrastructure failure. The version's enabled skills (Skills, below) are its pinned versions (`SkillsService.forRun`; one gone fails without retrying): they're in the agent's Mastra `Workspace` through `InMemorySkillSource` (`/skills/<name>/…`, read-only, from memory), so Mastra gives the agent its skill tools (`skill`, `skill_read`, `skill_search`), the prompt lists them (name and description, and to read one before doing what it's for), and with a sandbox their files are also copied to `/workspace/skills/<name>` (one `sh -c` per file through `SandboxDriver.exec` stdin, before each run) so their scripts can run; a version without a sandbox still gets a workspace for them. With a sandbox and Loculus (`LOCULUS_URL`), the agent also gets `submit_file` (a path, relative to `/workspace` or absolute; title, optional `fileName`, `contentType` (else from the extension), `primary`, `revises`): `SandboxFiles` reads it out of the sandbox (`exec`, `head -c` one byte past `TASK_FILE_MAX_BYTES`; not a file, too large or an invalid type is a tool error the agent sees) and `FileStore` (`LoculusFileStore`, the generated Loculus client with the task token: declare, `PUT` the bytes to the signed URL, complete; `NoFileStore` without `LOCULUS_URL`) keeps it, then it's recorded as a `file` artifact. With a sandbox, the prompt says the sandbox is deleted when the task ends and what is kept (`withKeeping`); a file sent back for revision is described, not inlined. Mastra's model registry drops settings it believes a known model doesn't support (e.g. `temperature`).

- **Verification (`TaskRunner.runAndVerify`, `Verifier`, `../docs/tasks.md` Verification):** part of every execution, after each run of the agent and before its sandbox goes. A check that can't run throws (infrastructure failure, never a pass). The round is recorded as a `verification` artifact (`round`, `results`; never primary, never a draft) and `task.verified` (on the task's event stream, for Kriterion). A task without criteria still records an empty round. - **Sandboxes (`libs/runner`):** `SANDBOX_DRIVER=docker` gives `WorkspaceSandboxProvisioner` (else `NoSandboxProvisioner`: versions with `runtime.sandboxRequired` fail without retrying). For each such execution it records a **workspace** (`WorkspacesService.createForExecution`, then `startProvisioning`, `markReady`, `acquireForExecution`; at the end `destroyForExecution` and `markDestroyed`, or `markFailed`; no caller, no permission check), with no repository, the sandbox settings, `the network access (`none`, or `restricted` with its `allowedHosts`: `SANDBOX_ALLOWED_HOSTS` plus the version's) and `/workspace`, and has the `SandboxDriver` create the sandbox, keyed by the execution ID (idempotent). Before destroying it, it records the hosts the sandbox's proxy refused on the workspace (`blockedHosts`, `WorkspacesService.recordBlockedHosts`). The executions list shows each execution's `sandbox` (its workspace, network access, allowed and blocked hosts; `WorkspacesService.sandboxesOf`), so people with `task:read` see what an agent was refused without `workspace:read`. `DockerSandboxDriver` creates the container itself with Docker's API (Mastra's `DockerSandbox` can't set the user): `SANDBOX_USER`, all capabilities dropped, `no-new-privileges`, read-only root filesystem with tmpfs `/workspace` (`SANDBOX_WORKSPACE_MB`, mode 0700, executable: a repository's scripts and Git hooks run there) and `/tmp` (`noexec`), the image's entrypoint replaced (`sleep infinity`), PID, memory (no swap) and CPU limits, an init process, no environment from Hephaestus (only `HOME`, and `HTTP(S)_PROXY` for a `restricted` one), and **no network**, unless the version has `runtime.networkAccess: restricted`: then the sandbox's only network is an internal Docker network of its own (`aether-sandbox-net-<execution>`, no route out) shared with its **egress proxy** (`aether-sandbox-proxy-<execution>`, `SANDBOX_PROXY_IMAGE`, as hardened, also on `SANDBOX_EGRESS_NETWORK`), which runs `egress-proxy.ts` (a Node script, `node -e`: `CONNECT` tunnels and plain HTTP to allowed hosts on ports 80 and 443, connecting to the address it resolved itself, refusing private, loopback and link-local addresses and everything else with a `403`, and logging each refusal as a JSON line, which `blockedHosts` reads back); the proxy and the network go with the sandbox, labels `aether-os.*` (organization, project, task, execution, workspace); then Mastra's `DockerSandbox` attaches to it by label. Failing to create is a retryable infrastructure failure (the half-made container is removed, the workspace `failed`). Tests run real containers (`docker-sandbox.int-spec.ts`, `alpine:3.20`; proxies from `mirror.gcr.io/library/node:22-alpine`, set in `test/setup.ts`, since Docker Hub rate-limits), including a `restricted` sandbox against a stand-in registry on a test egress network; `egress-proxy.spec.ts` runs the proxy script in a child process.
- **Models through Pylon (`libs/models`, `../docs/pylon.md`):** Hephaestus calls no provider itself and holds no key, catalogue, metering or budget; `libs/models` is Pylon's client (`PYLON_URL`):
  - **Models** (`ModelGateway.resolve`, `PylonModels` → `HttpPylonModels`): the provider's own AI SDK client (`@ai-sdk/anthropic`, `openai` (Responses), `google`, `mistral`, or the OpenAI-compatible one for Ollama and anything else) with its `baseURL` at Pylon's pass-through (`<PYLON_URL>/v1/providers/<provider>/…`), the **task token** as its key and `X-Aether-Execution-Id`. Pylon checks the model against its catalogue and the task's budgets, picks the key (the agent's, the organization's, the platform's), meters the call and retries it before answering, so the AI SDK doesn't (`maxRetries: 0`). Task tokens carry `task_tree_id`, `agent_id` and `agent_version_id` (`ExecutionPreparer.token`); the task's service account needs `model:invoke` in the project (`editor` and above). Tests: `pylon-models.spec.ts` (every provider's request at a local server).
  - **Pylon's answers in the runtime** (`failureOf` / `pylonBudget` in `mastra-agent-runtime.ts`): `402 BUDGET_EXHAUSTED` pauses the task (`BudgetExceededError` with the budget's scope); the provider or Pylon refusing (400, 401, 403, 404, `409`: no key, a retired model) fails without retrying; 429, 5xx and no answer are retryable infrastructure failures.
  - **Budgets** (`Pylon` → `HttpPylon`, the generated client in `libs/core/src/clients/pylon`, `PylonUnavailableError` (`503`) when Pylon or Pistis doesn't answer; Pylon's 4xx problem details passed on): `exhausted(task)` is Pylon's `budget-checks` with Hephaestus's own token (`ServiceTokens`, `platform:read`), asked before an execution starts (`ExecutionPreparer.assertBudget`) and each round for paused tasks (`PausedTasks.resume`: room again → `queued`, `task.resumed`, `reason: budget-available`). A task tree's budget is Pylon's, by its top-level task's ID: `TaskBudgetsService` sets it with the **caller's own token** (Pylon checks `task:create`), from `budgetUsd` when a top-level task is created (before the task's transaction commits: Pylon refusing rolls the task back) and from `PUT …/tasks/{taskId}/budget`, and reads it with Hephaestus's own (`GET …/tasks/{taskId}/budget`); a `task.create` command can't carry `budgetUsd` (`TASK_BUDGET_INVALID`), there being no token of the sender's. `BudgetExceededError` → `ExecutionsService.pause`: the execution ends `paused`, its pending artifacts `partial`, the task `paused` with `pausedFor` (`task.paused`).
  - **Usage** (`usageOf`): the executions list's `usage` is Pylon's `GET …/usage?groupBy=execution&executionId=…` (100 at a time).
  - Hephaestus's old tables (`models`, `model_prices`, `model_keys`, `budgets`, `model_calls`) stay in its database, unused, until Pylon's `pnpm import:hephaestus` has copied them; a later migration drops them.
  - Tests replace `Pylon` and `PylonModels` with `test/fake-models.ts` (`FakePylon`: `exhaustedScope`, tree budgets, usage from the calls; `ScriptedPylonModels`: a scripted AI SDK v2 model recording the token and execution of each; `budgetExhausted` for Pylon's 402), in every test app (`test/app.ts`, `test/testing-module.ts`).
- **Health** (`../docs/engineering.md`, Health checks): `/health` checks the database, RabbitMQ, Pistis, Polis, Pylon, Proxenos, Loculus and Seshat (when set), OpenBao (when set), and with `SANDBOX_DRIVER=docker` the Docker engine (`docker`, `DockerSandboxDriver.ping`, registered by `RunnerModule`); only the database is required.
- **Errors:** `DomainError` subclasses become `409` problem details with their `code`; add new codes to the spec's `DomainErrorCode` enum too.

### API contract

Spec-first: `../contracts/hephaestus.openapi.yaml`. `pnpm generate:api` runs `@hey-api/openapi-ts` (`openapi-ts.config.ts`) for Hephaestus's own types and Zod schemas (`libs/core/src/api/generated/`) and for HTTP clients of Polis (`libs/core/src/clients/polis/generated/`, `PolisApi`), Proxenos, Loculus and Pylon (`PylonApi`: budget checks, task trees' budgets, usage), and `aether-asyncapi-types` for Polis's event payloads and Hephaestus's own (`libs/core/src/events/generated/`, exported as `PolisEvents` and, for its own, `HephaestusEvents` with `HEPHAESTUS_PUBLISHED_EVENTS`, and the commands it accepts, `HEPHAESTUS_COMMAND_TYPES`). All committed, formatted, never hand-edited (the generated client is excluded from lint); Iris generates its types from the Hephaestus spec. To change an endpoint: edit the spec, regenerate (here and in `../iris`), then update the DTO classes, mapper and controller.
