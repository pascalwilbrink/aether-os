# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Hephaestus is the Aether-os service that runs agents (see `../CLAUDE.md`). Today it holds **agents** with immutable, numbered **versions** (instructions, model, tools, skills, runtime; draft → published → deprecated, one published at a time), **workspaces**: sandboxed execution environments in a project, driven by user actions and provisioner callbacks, **tasks**: the work an agent does (`../docs/tasks.md`), with their lifecycle, the **runner** that executes them (`libs/runner`), running agents with Mastra, and the **model gateway** (`libs/models`) their model calls go through, with provider keys from OpenBao. Executions that need a sandbox get a hardened Docker container, recorded as a workspace, with shell tools for the agent; what agents produce are **artifacts** (`libs/artifacts`); tasks can come from **task templates** (`libs/templates`). No configured tools or skills yet. Organizations and projects belong to **Polis**: Hephaestus keeps only their status (`libs/tenancy`), from Polis's events, and asks Polis's API about one it hasn't seen yet.

Target role: Hephaestus is the task runner. Agents move to Agora; the runner gets [Mastra](https://mastra.ai) as its agent runtime and sandbox layer, behind the ports it already has (`AgentRuntime`, `SandboxProvisioner`).

It follows `../docs/engineering.md` like Polis: NestJS 12 (ESM, TypeScript 6), controller → service → TypeORM repository with mappers, Zod DTOs generated from the spec, `typeorm-transactional`, Postgres with migrations, tests against Postgres in containers.

## Commands

```bash
pnpm install                   # from the workspace root (../)
cp .env.example .env           # once; then `docker compose up -d` in ../ for Postgres
pnpm start:dev                 # build, run migrations, then watch mode on $PORT (default 3002)
pnpm build
pnpm lint                      # oxlint --type-aware; no-floating-promises is an error
pnpm format                    # prettier (single quotes, trailing commas)
pnpm generate:api              # regenerate libs/core/src/api/generated from ../contracts/hephaestus.openapi.yaml

pnpm migration:run             # apply pending migrations (on dist/: build first)
pnpm migration:show
pnpm build && pnpm migration:generate src/database/migrations/<Name>   # then review it and add it to migrations/index.ts

pnpm test                      # unit tests (libs/**/*.spec.ts): transition tables, mappers, config; no database
pnpm test:e2e                  # integration (libs/**/*.int-spec.ts) and e2e (test/*.e2e-spec.ts) against Postgres; needs Docker
pnpm test libs/workspaces/src/workspace-transitions.spec.ts   # single file
pnpm test:e2e -t "publishes"   # filter by test name
```

## Configuration

Environment variables, validated at startup with the Zod schema in `libs/core/src/config/env.ts` (`hephaestusConfigModule()`, through Krepis's `validateEnv`): `DATABASE_URL` (required, Postgres), `POLIS_URL` (required, Polis's API), `RABBITMQ_URL` (required; Polis's events), `PISTIS_ISSUER` (required: whose tokens to trust), `PISTIS_JWKS` (optional: trusted keys instead, tests), `PISTIS_CLIENT_ID` (`hephaestus`) and `PISTIS_CLIENT_SECRET` (required: Hephaestus's own client at Pistis, for its calls to Polis), `OUTBOX_RELAY_INTERVAL_MS` (1000), `PORT` (3002), `NODE_ENV`. The runner: `AGENT_RUNTIME` (`none`, the default, starts no runner; `mastra` runs agents; `echo` finishes every task at once without a model, for local development), `RUNNER_POLL_INTERVAL_MS` (1000), `RUNNER_MAX_EXECUTIONS` (4 per instance), `RUNNER_MAX_TASKS_PER_ORGANIZATION` (10) and `RUNNER_MAX_TASKS_PER_PROJECT` (5), `RUNNER_PROVISIONING_TIMEOUT_MS` (10 minutes), `RUNNER_RUN_TIMEOUT_MS` (60 minutes), `RUNNER_HEARTBEAT_INTERVAL_MS` (15 s), `RUNNER_HEARTBEAT_TIMEOUT_MS` (2 minutes), `RUNNER_STOP_GRACE_MS` (30 s), `RUNNER_MAX_INFRASTRUCTURE_FAILURES` (3) and `RUNNER_RETRY_BACKOFF_MS` (10 s, doubled per retry), `REVIEW_MAX_ROUNDS` (3), `VERIFICATION_MAX_ROUNDS` (3). The model gateway: `OPENBAO_ADDR` and `OPENBAO_TOKEN` (required with `AGENT_RUNTIME=mastra`), `OPENBAO_KV_MOUNT` (`secret`), `PLATFORM_MODEL_KEYS` (false: whether organizations without their own key may use the platform's). Sandboxes: `SANDBOX_DRIVER` (`none`, the default: versions that need a sandbox fail; `docker`: the local Docker engine, `DOCKER_HOST` or its socket), `SANDBOX_IMAGE` (`node:22-slim`; needs `sh`, and `git` for tasks that work in a repository), `SANDBOX_USER` (`1000:1000`; never root), `SANDBOX_CPUS` (1), `SANDBOX_MEMORY_MB` (2048), `SANDBOX_PIDS_LIMIT` (256), `SANDBOX_WORKSPACE_MB` (1024), and for `restricted` network access `SANDBOX_ALLOWED_HOSTS` (comma-separated, `*.` for subdomains; default the npm, PyPI, Go, crates.io, Maven and RubyGems registries), `SANDBOX_PROXY_IMAGE` (`node:22-alpine`) and `SANDBOX_EGRESS_NETWORK` (`bridge`). Repositories: `PROXENOS_URL` (Proxenos's API, for repository tokens; without it tasks that work in a repository fail). Locally they come from `.env` (gitignored; `.env.example` has the defaults for `docker compose`).

## Running agents locally

`AGENT_RUNTIME=mastra` in `.env`, then set the organization's provider key in Iris (the organization's **Model keys** page) or with `PUT /v1/organizations/{id}/model-keys/{provider}`. The development OpenBao is in memory, so keys are gone after it restarts while their rows remain: set them again. For the platform's key, with `PLATFORM_MODEL_KEYS=true`:

```bash
curl -s -X POST http://localhost:8200/v1/secret/data/platform/llm/anthropic -H 'x-vault-token: dev-root-token' \
  -d '{"data":{"apiKey":"sk-ant-..."}}'
```

An agent version's model is then `{ "provider": "anthropic", "model": "<model>" }`, with a model ID Mastra's model router knows for that provider. The task's service account needs a role in the task's project (Pistis's task token). For an agent that works in a shell, set `runtime.sandboxRequired` on its version and `SANDBOX_DRIVER=docker` (and `runtime.networkAccess: restricted` for one that installs packages): each execution then gets its own container (`docker ps --filter label=aether-os.sandbox=true`).

## Database

- **Postgres**, Hephaestus's own database (`hephaestus` in `../docker-compose.yml`), connected in `libs/core/src/database/database.module.ts` with Krepis's `postgresOptions` and `createTransactionalDataSource`.
- **Migrations only:** `src/database/migrations/` (registered in `migrations/index.ts`, oldest first), run by `pnpm migration:run` as a separate step, never at startup. The TypeORM CLI uses `src/database/data-source.ts` (compiled to `dist/`); list new entities there and in `test/global-setup.ts`. No down migrations: keep them compatible with the previous release.
- **Columns:** `uuid` IDs, `timestamptz`, `text`, enums as `text` with a check constraint, configuration objects as `jsonb`, and an index matching each keyset pagination.
- **Tests** run against Postgres 17.5 and RabbitMQ 4.1 in containers started once per `test:e2e` run (`test/global-setup.ts`): it applies the migrations and fails if the entities differ from the migrated schema. Files run one at a time; every test starts from emptied tables (`test/database.ts`). Tokens come from the run's `TestTokens` (`test/tokens.ts`, trusted through `PISTIS_JWKS` in `test/setup.ts`; `asMember` in `test/auth.ts`); integration tests use `actingAs(service, testPrincipal(...))`. Test apps replace `PolisClient` with `test/fake-polis.ts` (organizations and projects as Polis would return them) and deliver Polis's events through the real inbox (`deliverPolisEvent`, `organizationEvent`, `projectArchived`); `test/polis-events.e2e-spec.ts` goes through RabbitMQ.

## Architecture

`src/` is the app shell: `main.ts` calls Krepis's `initializeTransactions()` before Nest boots and `configureHttpApp(app)` (the `/v1` prefix, Zod validation, the response serializer, problem details); `app.module.ts` imports the config, database and feature modules. Code lives in Nest libraries under `libs/`, registered in `nest-cli.json` and aliased in `tsconfig.json` as `@hephaestus/<name>`.

Dependency graph: `core` ← `tenancy` ← `agents`, `workspaces`; `tenancy`, `agents` ← `tasks` ← `artifacts`; `tasks`, `artifacts`, `models`, `workspaces` ← `runner`; `agents`, `tasks`, `tenancy` ← `templates`. The runner reaches Proxenos with the generated client (`libs/core/src/clients/proxenos`, `ProxenosApi`). A library's `index.ts` exports its module, services and errors, never entities, mappers or repositories.

Each feature library has the layout described in `../polis/CLAUDE.md`: `*.module.ts`, `*.controller.ts` (routes only), `*.service.ts` (rules, `@Transactional()`, tenancy; returns response DTOs), `*.entity.ts`, `*.mapper.ts` (UUIDv7 IDs), `*-transitions.ts` (the lifecycle as a pure table, tested exhaustively), `*.errors.ts` and one-line `createZodDto` classes in `dto/`.

- **Tenancy (`libs/tenancy`):** `OrganizationsService.assertExists` (reads: 404) and `assertAcceptsWrites` (writes: 404 or `ORGANIZATION_SUSPENDED`); workspaces are created through `ProjectsService.assertAcceptsWrites` (also `PROJECT_ARCHIVED`, and 404 for another organization's project). They read `organization_states` / `project_states`, Hephaestus's copy of Polis's state:
  - kept from Polis's events (`organization.created` / `.suspended` / `.reactivated`, `project.created` / `.archived`), consumed through Krepis's `EventsModule` subscription in `app.module.ts` (`POLIS_SUBSCRIPTIONS`; queue `hephaestus.polis-events`, inbox, retries, dead-lettering) and handled with `@OnDomainEvent('polis.<eventType>')`;
  - on a miss, fetched once from Polis's API through `PolisClient` (`HttpPolisClient`: the client generated from Polis's spec, 5 s timeout, one retry), which also covers organizations created before Hephaestus subscribed. Polis unreachable then is `503 UNAVAILABLE`;
  - every write is version-guarded (`aggregateVersion` for events, Polis's `version` for fetches): a late, repeated or older event never moves a state backwards.
  Everything is looked up within its organization, so another organization's resource is a 404.
- **Access** (`../docs/identity.md`, Krepis `AuthModule` in `app.module.ts`; `x-permission` in the spec): agents need `agent:read`, `agent:write` (create, archive, new versions) and `agent:publish`; `createdBy` is the caller's `sub`. Workspace routes need an organization token (`org:read`), and `WorkspacesService` checks the project permission once the project is known: `workspace:read` to read, `workspace:manage` to create (the body's project) and for user actions; lists hold only workspaces in projects the caller can read; provisioner callbacks have no caller and no check.
- **Calling Polis:** `HttpPolisClient` sends Hephaestus's own token (`ServiceTokens`: `ClientCredentialsServiceTokens` with `PISTIS_CLIENT_ID` / `PISTIS_CLIENT_SECRET`, scope `platform:read`); no token from Pistis is `503 UNAVAILABLE`, like Polis being down.
- **Agents and versions:** `AgentsService` owns agents, `AgentVersionsService` owns versions and reaches agents through `AgentsService`. Creating or publishing a version calls `lockForVersionChange`, which locks the agent row (`AGENT_ARCHIVED` for archived agents): concurrent requests for one agent take turns, so version numbers are gapless and only one version is published. Publishing deprecates the previous published version in the same transaction; publishing the published version returns it unchanged; a deprecated version can't be published (`AGENT_VERSION_INVALID_TRANSITION`). Archiving an agent is idempotent.
- **Workspaces:** `workspace-transitions.ts` lists every allowed (status, action) pair; anything else is `WORKSPACE_INVALID_TRANSITION`. Workspace transitions are strict, not idempotent. User actions (acquire, release, suspend, resume) need an active organization; destroy only an existing one (a suspended organization can still release resources); provisioner callbacks (`startProvisioning`, `markReady`, `markDestroyed`, `markFailed`, `expire`, service methods without HTTP routes) skip the check, as do the runner's own (`createForExecution`, `acquireForExecution`, `destroyForExecution`). `repository` is optional (an execution's sandbox has none yet). `expiresAt` must be in the future (`WORKSPACE_INVALID_EXPIRY`).
- **Tasks (`libs/tasks`, `../docs/tasks.md`):** `/v1/organizations/{organizationId}/projects/{projectId}/tasks`: create (`task:create`), list (by `parentTaskId`, `status`) and read (`task:read`), `cancel` (`task:cancel`) and `retry` (`task:create`), all in the route's project (Krepis: no role there is a 404).
  - **Creating** needs an `Idempotency-Key` header: the same key in the organization returns the task it created (`200`) instead of a second one (also when two requests race: the unique constraint decides). The agent's published version is pinned (`AgentsService.publishedVersion`: `AGENT_NOT_PUBLISHED`, `AGENT_ARCHIVED`), the project must accept writes, `review.artifactKinds` (kinds whose artifacts need approval, `*` for all) and `acceptanceCriteria` (unique `key`s, else `TASK_CRITERIA_INVALID`; `source: task`) are pinned on it, and the task runs as `serviceAccountId` (a Pistis service account; tasks never run as a user) with the caller recorded as `requestedBy`.
  - **Concurrency keys** (`../docs/tasks.md` Concurrency): `concurrency: { key, policy }` on a top-level task (`TASK_CONCURRENCY_INVALID` on a subtask; also from templates and commands), stored as `concurrency_key` / `concurrency_policy`. `TasksService.create` takes an advisory lock on the project and key for the transaction, then looks for unfinished tasks of the project with that key: `skip` refuses (`TASK_CONCURRENCY_SKIPPED`), `cancel-previous` cancels them (as `cancel` does, subtrees too), `queue` creates it anyway, and `TaskQueue.claimNext` skips a queued task while an older unfinished one (by `created_at`, `id`) has its key.
  - **Repository** (`../docs/git.md`): `repository: { linkId }` names one of the project's repository links in Proxenos (checked when the task runs, not when it's created); a subtask without one works in its parent's, since a task tree shares a branch. Tasks from templates take it from the request.
  - **Trees:** `parentTaskId` makes a subtask (not under a finished task: `TASK_PARENT_FINISHED`); every task records its `topLevelTaskId`. `dependsOn` may only name tasks under the same top-level task (`TASK_DEPENDENCY_INVALID`; a top-level task has none). A task starts `blocked` until all its dependencies have succeeded, else `queued`; when a task succeeds, its blocked dependents whose dependencies have all succeeded become `queued`.
  - **Lifecycle:** `task-transitions.ts`, every (status, action) pair of the lifecycle in `docs/tasks.md`, tested exhaustively; anything else is `TASK_INVALID_TRANSITION`. People `cancel` (the task and every unfinished task under it; idempotent; a suspended organization can still cancel) and `retry` (a failed task, same pinned inputs, `attempt` + 1, back to `queued` or `blocked`). The runner moves tasks with `TasksService.transition` (no HTTP route); `fail` needs a `failureReason`, `requeue` (an infrastructure failure retried) takes the backoff as `notBefore` (`nextAttemptAt`), `await-review` takes the drafts (`reviewRound` + 1, `task.awaiting-review`), `revise` (changes requested) queues it again.
  - **Events** (`../contracts/hephaestus.asyncapi.yaml`, `HephaestusEvents` in `@hephaestus/core`): `task.created`, `task.status-changed` (from, to, reason) on every change, and `task.succeeded` / `task.failed` / `task.cancelled`, in the change's transaction (outbox → `hephaestus.events`). `version` on a task is its events' `aggregateVersion`.
- **Runner (`libs/runner`, `../docs/tasks.md` Task lifecycle):** every instance runs one `TaskRunner` (when `AGENT_RUNTIME` isn't `none`), all on the same tables, so instances can come and go.
  - **Claiming** (`TaskQueue` in `libs/tasks`, through `ExecutionsService.claim`): a `queued` task whose backoff has passed, locked `FOR UPDATE SKIP LOCKED` (no two instances take the same task); the organization with the fewest running tasks first, then subtasks, then oldest; within `RUNNER_MAX_TASKS_PER_ORGANIZATION` / `_PER_PROJECT`, counted under a per-organization advisory lock; never in a suspended organization or archived project (those tasks wait). The claim moves the task to `provisioning` and records its **execution** in the same transaction.
  - **Executions** (`executions` table; `GET …/tasks/{taskId}/executions`, `task:read`): one per try, numbered within the task, with the task's `attempt`, `status` (`provisioning`, `running`, `completed`, `failed`, `cancelled`, `paused`), `failureReason`, `error`, `summary` (the agent's final answer), the sandbox reference, `heartbeatAt` and `deadlineAt`. At most one active per task (a partial unique index). Every change to an execution and its task's transition is one transaction, execution row locked first; an execution that already ended changes nothing (`ExecutionsService`).
  - **Running one** (`TaskRunner.execute`): the pinned agent version, a task token (`TaskTokens` → `PistisTaskTokens`: token exchange as Hephaestus's own client; refused → `access_denied`, no retry; the token's `org_id` must be the task's organization), a sandbox if the version needs one (`SandboxProvisioner`, below), then `running` with the run deadline, then the `AgentRuntime` port (`AGENT_RUNTIME`: `MastraAgentRuntime`, or `EchoAgentRuntime`, which calls no model). Completed → `verifying` (Verification, below) → `delivering` → `succeeded` (nothing to deliver yet) with the execution's artifacts `final` and its primary artifact on the task (`primaryArtifactId`; without any outcome the task fails `agent_failed`), or, when some need approval, → `awaiting_review` with them as drafts (Reviews, below); the agent giving up → `agent_failed`. The runtime gets an `ArtifactSink` bound to the execution (`ExecutionsService.recordArtifact`, refused once the execution ended); a failed or cancelled execution's pending artifacts become `partial`. Whatever the execution left behind is destroyed, found by its execution ID (also when provisioning was abandoned).
  - **Failures** (`RunnerFailure` from the ports: a reason and whether retrying helps; anything else thrown is a retryable infrastructure failure): a retryable infrastructure failure requeues the task (`requeue`) with backoff while the attempt has had fewer than `RUNNER_MAX_INFRASTRUCTURE_FAILURES`, then fails it `infrastructure`; an execution interrupted by shutdown is requeued without counting.
  - **Stopping:** the runtime gets an `AbortSignal`, aborted at the run deadline (`timeout`), the provisioning timeout (infrastructure), a cancelled task (seen at the next heartbeat; the execution ends `cancelled`), a lost execution, or shutdown; after `RUNNER_STOP_GRACE_MS` it's abandoned.
  - **Heartbeats and the reaper:** each instance refreshes `heartbeatAt` of its executions; each poll, `ExecutionReaper` ends any instance's executions past the heartbeat or provisioning timeout (infrastructure, retried) or the run deadline (`timeout`), and destroys their sandboxes.
  - **Tests** override `RUNNER_OPTIONS` (`testRunnerOptions`: no polling) and the ports with `test/fake-runner.ts`, and drive rounds with `tick()`, `heartbeat()` and `drain()`.
- **Repositories in sandboxes (`RepositoryCheckouts`, `../docs/git.md` Inside the sandbox):** for a task with a repository, after its sandbox is provisioned (within the provisioning timeout): the sandbox must have `git` (else the execution fails without retrying, as it does for a version without a sandbox); a **read** token comes from Proxenos (`RepositoryTokens` → `HttpRepositoryTokens`, the generated Proxenos client, with the **task's own token**; 403/404 → `access_denied`, 409 → infrastructure without retrying, otherwise retried); `GitClient` (the `git` CLI on Hephaestus's side, no user or system config, credentials only in `GIT_CONFIG_*` environment variables, never on the command line) clones it fully into a temporary directory, from the task tree's branch `aether/<topLevelTaskId>` if the remote has it (the work of finished dependencies) or else the default branch; and the clone goes into the sandbox as a git bundle through `docker exec` stdin (`SandboxDriver.exec`, bytes in and out: `docker cp` reaches neither tmpfs nor a read-only root). In the sandbox it is `/workspace/repo`, on the task branch, without a remote, committing as `Aether-os <aether-os@users.noreply.github.com>`, with a `commit-msg` hook adding `Aether-Task: <task ID>`; **the sandbox never sees a token and still has no network**. The execution records `repository` (link, `fullName`, `branch`, `baseSha`), the runtime gets `repository` (the Mastra prompt says where it is and that only commits are kept). When a run passes verification, before completing: the commits on top of the base come out as a bundle through `docker exec` stdout, are verified and fetched into Hephaestus's clone (`refs/aether/result`; bundles from sandboxes run with hooks and fsmonitor off) and must descend from the base (else `agent_failed`); the execution records `headSha`, `commits` and `uncommittedChanges` (not kept). Then **they're pushed** (`RepositoryCheckouts.push`, `../docs/git.md` Branches and pull requests): commits that change `.github/workflows` are refused (`agent_failed`; the app has no `workflows` permission anyway); a **write** token comes from Proxenos; only `aether/*` branches, **never forced**: if the branch moved since the checkout (a sibling subtask pushed) the commits are rebased onto it first (as the Aether-os committer), and a push that loses a race is tried again (3 times); a rebase conflict goes **back to the agent** (`BranchConflictError`, then `RepositoryCheckouts.startConflictResolution`): the branch's new commits go into the sandbox as a bundle (`refs/aether/upstream`), the agent's commits are rebased onto them there (`--autostash`), stopping at the conflicts; the checkout's base becomes the branch's head, the task goes back to `running` (`ExecutionsService.returnToAgent`, `reason: branch-conflict`), and the agent runs again with `conflict` (the branch and the conflicted files; the Mastra prompt says to resolve them and run `git rebase --continue`), is verified again, and its commits are collected and pushed again. A rebase left unfinished fails the execution `agent_failed`. Conflicts share the execution's `VERIFICATION_MAX_ROUNDS`; once they're used up, the execution fails as a retryable infrastructure failure and the next one starts from the branch's head. The execution records `pushedSha`, and the commits become a **`pull_request` artifact** (Hephaestus's own, `ArtifactsService.record` with `NewPullRequest`; never from the agent's tool): the task's title, the run's summary plus `Aether-Task` as the description, the branch, `baseBranch` (the default branch), `headSha` (the pushed head), `pullRequest: null` until delivery opens it; primary (the outcome of a coding task), revising the `pull_request` a reviewer sent back in a revision run, and a draft like any artifact when `review.artifactKinds` names `pull_request` (the branch is pushed already: a draft is the branch at its head). Nothing committed: nothing pushed, no `pull_request`. Hephaestus's clone is removed when the execution ends. Commits are made as the GitHub App's bot (`committer` from Proxenos's token response: `<slug>[bot]` and its noreply email), in the sandbox and when rebasing.
- **Delivery and branch cleanup (`Deliveries`, `../docs/git.md`):** a task whose final artifacts include a `pull_request` not opened yet stays `delivering` (from `ExecutionsService.complete` or an approval in `ReviewsService`) instead of succeeding at once. Each runner round (`TaskRunner.round`, before claiming tasks) delivers what's due: `TaskQueue.claimDelivery` takes a `delivering` task (`FOR UPDATE SKIP LOCKED`, `next_attempt_at` as a 5-minute lease, `delivery_attempts` counted), `TaskRepositoryAccess` gets a write token (a short task token, then Proxenos), and the `PullRequests` port (`GitHubPullRequests`, GitHub's REST API at Proxenos's `apiUrl`) opens each pull request, or adopts and updates the branch's open one (a `422` on creating), recording `pullRequest` (number, URL, state) on the artifact; then the task succeeds (`reason: delivered`, its latest final primary artifact). A retryable failure waits `RUNNER_RETRY_BACKOFF_MS`, doubled per try, up to `RUNNER_MAX_INFRASTRUCTURE_FAILURES` tries; refused access or the last try fails the task (`infrastructure`, `reason: delivery-failed`). Proxenos's `git.pull-request.updated` (subscribed in `app.module.ts`, `PROXENOS_SUBSCRIPTIONS`; `ArtifactsService.onPullRequestUpdated`) keeps the artifact's `pullRequest.state` in step; a merged or closed pull request, and a top-level task with a repository that fails or is cancelled, set `branch_cleanup_at` on the tree's top-level task, and the round deletes `aether/<top-level task ID>` (`GitClient.deleteBranch`; gone already is fine; retried every 10 minutes on failure; given up when access is refused). Tests: `repositories.int-spec.ts` (real hardened containers with `alpine/git`, a local bare repository as the remote: checkout, commits out, pushes, rebases onto a moved branch, conflicts resolved by the agent, an unfinished rebase, conflicts past the rounds, workflows refused, review).
- **Mastra runtime (`libs/runner/src/mastra-agent-runtime.ts`):** the pinned agent version becomes a Mastra `Agent` (its instructions, and the model from `ModelGateway.resolve`); the input is the task's title and instructions; `generate` runs with the execution's `AbortSignal`, up to 20 steps, the version's `temperature` and `maxTokens`, and 2 retries of a model call on 429 and 5xx. Each step (one model call) is metered through `onStepFinish`; the final text is the execution's `summary`. The agent always gets `submit_artifact` (kind `text` or `json`, title, content as text, `format`, `schema`, `primary`; JSON content is parsed here, invalid JSON or a broken limit is a tool error the agent sees). Failures: no key, or the provider refusing the call (400, 401, 403, 404) fail without retrying; OpenBao or the provider being unreachable or overloaded is a retryable infrastructure failure. With a sandbox, the agent gets a Mastra `Workspace` on it: shell tools only (run a command, read a background process's output, stop it), and files through the shell, since Mastra's only filesystem is the host's. A version that enables configured tools or skills fails without retrying until they're supported. Mastra's model registry drops settings it believes a known model doesn't support (e.g. `temperature`).
- **Artifacts (`libs/artifacts`, `../docs/tasks.md` Artifacts):** `GET …/tasks/{taskId}/artifacts` (oldest first, by `status`) and `…/artifacts/{artifactId}`, `task:read` in the project. An artifact has the common fields (task, execution, `agentVersionId` copied from the task, `kind`, `status`, `primary`, `revisionOf`, `title`, `metadata`, `version`) and its kind's own in `body` (jsonb): `text` (`format`, `content`), `json` (`schema`, `content`) and `pull_request` (Hephaestus's own, below; its `pullRequest` is the one part that changes, with delivery and GitHub's state), inline up to 256 KiB (`MAX_CONTENT_BYTES`), at most 50 per execution. Its content never changes. `ArtifactsService.record` stores it `pending` (`artifact.created`; marking one primary clears the execution's other pending primaries), `complete` turns an execution's pending artifacts `final` (`artifact.status-changed`) with exactly one primary: the one the agent marked, else its final answer as a new text artifact (`Answer`), else its latest artifact; nothing at all is no outcome. `abandon` turns them `partial`, never primary. A partial unique index allows one final primary artifact per task. The single-artifact response is a union on `kind`, so its route serializes with `zArtifactResponse` (no DTO class).
- **Verification (`TaskRunner.runAndVerify`, `Verifier`, `../docs/tasks.md` Verification):** part of every execution, after each run of the agent and before its sandbox goes. The run's outcome is settled first (`ArtifactsService.settle`: the primary artifact; a later final answer replaces an earlier one), the task moves to `verifying`, and `Verifier` checks each criterion: `command` with the sandbox's `executeCommand` (exit code 0 passes; timeout, 300 s by default; the last 16 KiB of output kept), `artifact` on the run's pending and the task's final artifacts (`primaryKind`, `titles`), `manual` left to the reviewer. A check that can't run throws (infrastructure failure, never a pass). The round is recorded as a `verification` artifact (`round`, `results`; never primary, never a draft) and `task.verified` (on the task's event stream, for Kriterion). Any failure: back to `running` and the agent runs again in the same execution and sandbox with `failedChecks` (the Mastra runtime lists them in the prompt), up to `VERIFICATION_MAX_ROUNDS` runs, then the execution fails `verification_failed`. A task without criteria still records an empty round. Command checks need a version with `runtime.sandboxRequired` (else the execution fails without retrying, before the agent runs). `ExecutionPreparer` gives the runner the agent version, the task token and the sandbox. `judge` checks (Kriterion) aren't in the contract yet.
- **Task templates (`libs/templates`, `../docs/tasks.md` Task templates):** `/v1/organizations/{organizationId}/task-templates` (create with its first version, list, read, `archive`) and `…/{templateId}/versions` (a new version per edit; list, read with its `effective` content). Without `projectId` a template is organization-wide (`org:read` to read, `org:task-template:manage` to manage); with one it's that project's (`task:read` / `task-template:manage` there), and a project's list (`?projectId=`) has its own and the organization's (`scope`: the project's ID or `organization`, one filter). Routes only need `org:read`; `TaskTemplatesService` checks the scope. Versions are immutable `content` (`task_template_versions`); the effective content (`template-content.ts`, pure, unit-tested) adds what a project template `extends` (an organization-wide version of the same organization): its title and agent unless given, its instructions with the project's appended, inputs, criteria and review kinds added, never redefined (`TASK_TEMPLATE_INVALID`); placeholders (`{{name}}`) must be declared inputs, and its agent must exist. `POST /v1/organizations/{organizationId}/projects/{projectId}/task-templates/{templateId}/tasks` (`task:create`, `Idempotency-Key`; `TemplatedTasksService`) resolves a visible, active version (`TASK_TEMPLATE_ARCHIVED`; another project's is a 404), fills in the inputs (required, declared only: `TASK_TEMPLATE_INPUTS_INVALID`), and calls `TasksService.create` with the template origin: the task records `taskTemplateId` / `taskTemplateVersion`, its criteria are the template's (`source: template`) and the request's (`source: task`), its review kinds both.
- **Task commands (`TaskCommands` in `libs/templates`, `../docs/events.md` Commands):** `task.create` arrives on `hephaestus.commands` (`commands: HEPHAESTUS_COMMAND_TYPES` in `app.module.ts`; the contract is `../contracts/hephaestus.asyncapi.yaml`) as `commands.task.create`. Its payload is `task` (a `CreateTaskRequest`) or `template` (`templateId` and a `CreateTaskFromTemplateRequest`), checked with the HTTP API's own Zod schemas, plus `automationId`; it goes through `TaskBudgetsService.create` or `TemplatedTasksService.create`, like the HTTP routes, with the command's `eventId` as the idempotency key and the envelope's project, run as the sending service (`actor.sub` becomes `requestedBy`; `platform:read` for the reads) in a savepoint. Only `service` actors are accepted. The answer is `task.created`, published again for a command sent again, or `task.create-rejected` (`idempotencyKey`, `automationId`, the `code` the HTTP API would give) for one that can never succeed: invalid fields, an unknown or unpublished agent, an archived project, another organization's project. Anything else (Polis unreachable, the database) throws, and the consumer retries. Tests: `test/task-commands.e2e-spec.ts`.
- **Reviews (`ReviewsService` in `libs/artifacts`, `../docs/tasks.md` Request changes):** `POST …/artifacts/{artifactId}/approve`, `/reject` (optional `comment`) and `/request-changes` (`comments`, each a `body` and optional `anchor`), `task:approve` in the project, only on a `draft` (`ARTIFACT_NOT_DRAFT`), with an active project. The decision is stored on the artifact (`review`: decision, comments, `decidedBy`, `decidedAt`). Approving makes it `final` at once; rejecting fails the task `rejected`; requesting changes after `REVIEW_MAX_ROUNDS` rounds is refused (`TASK_REVIEW_ROUNDS_EXHAUSTED`). When no draft is undecided: any sent back → `revise` (the next execution gets them as `revisions`; the Mastra runtime adds them, content and comments, to the prompt, and the agent submits revisions with `revises` → `revisionOf`, which must name one of them), else `deliver` → `succeed` with every final artifact and the round's primary one. A failed or cancelled task's drafts and pending artifacts become `partial` (`onTaskEnded`, on the local `task.failed` / `task.cancelled`). One primary artifact per execution (round), so a revision can have a new one.
- **Sandboxes (`libs/runner`):** `SANDBOX_DRIVER=docker` gives `WorkspaceSandboxProvisioner` (else `NoSandboxProvisioner`: versions with `runtime.sandboxRequired` fail without retrying). For each such execution it records a **workspace** (`WorkspacesService.createForExecution`, then `startProvisioning`, `markReady`, `acquireForExecution`; at the end `destroyForExecution` and `markDestroyed`, or `markFailed`; no caller, no permission check), with no repository, the sandbox settings, `the network access (`none`, or `restricted` with its `allowedHosts`: `SANDBOX_ALLOWED_HOSTS` plus the version's) and `/workspace`, and has the `SandboxDriver` create the sandbox, keyed by the execution ID (idempotent). Before destroying it, it records the hosts the sandbox's proxy refused on the workspace (`blockedHosts`, `WorkspacesService.recordBlockedHosts`). `DockerSandboxDriver` creates the container itself with Docker's API (Mastra's `DockerSandbox` can't set the user): `SANDBOX_USER`, all capabilities dropped, `no-new-privileges`, read-only root filesystem with tmpfs `/workspace` (`SANDBOX_WORKSPACE_MB`, mode 0700, executable: a repository's scripts and Git hooks run there) and `/tmp` (`noexec`), the image's entrypoint replaced (`sleep infinity`), PID, memory (no swap) and CPU limits, an init process, no environment from Hephaestus (only `HOME`, and `HTTP(S)_PROXY` for a `restricted` one), and **no network**, unless the version has `runtime.networkAccess: restricted`: then the sandbox's only network is an internal Docker network of its own (`aether-sandbox-net-<execution>`, no route out) shared with its **egress proxy** (`aether-sandbox-proxy-<execution>`, `SANDBOX_PROXY_IMAGE`, as hardened, also on `SANDBOX_EGRESS_NETWORK`), which runs `egress-proxy.ts` (a Node script, `node -e`: `CONNECT` tunnels and plain HTTP to allowed hosts on ports 80 and 443, connecting to the address it resolved itself, refusing private, loopback and link-local addresses and everything else with a `403`, and logging each refusal as a JSON line, which `blockedHosts` reads back); the proxy and the network go with the sandbox, labels `aether-os.*` (organization, project, task, execution, workspace); then Mastra's `DockerSandbox` attaches to it by label. Failing to create is a retryable infrastructure failure (the half-made container is removed, the workspace `failed`). Tests run real containers (`docker-sandbox.int-spec.ts`, `alpine:3.20`; proxies from `mirror.gcr.io/library/node:22-alpine`, set in `test/setup.ts`, since Docker Hub rate-limits), including a `restricted` sandbox against a stand-in registry on a test egress network; `egress-proxy.spec.ts` runs the proxy script in a child process.
- **Model gateway (`libs/models`, `../docs/models.md`):** `ModelGateway.resolve` picks the key for the version's `provider` (a lowercase name, also the secret path's last part): the agent's own at `orgs/{organizationId}/agents/{agentId}/llm/{provider}`, else the organization's at `orgs/{organizationId}/llm/{provider}`, else, with `PLATFORM_MODEL_KEYS`, the platform's at `platform/llm/{provider}`; a key is stored as `{ "apiKey": "…" }`. It builds the model through the `LanguageModels` port (`MastraModelRouter`: Mastra's model router with that key, never env variables). `record` writes every call to `model_calls` (tokens with cache reads and writes, `keySource`, attribution, and its cost at the catalogue price `resolve` found, `priceId`; `model-cost.ts`: exact integer arithmetic in millionths of a dollar); `usageOf` totals them per execution (`usage` on executions, with `costUsd`, null when no call was priced). Secrets come through Krepis's `SecretStore` port (`OpenBaoSecretStore`, KV version 2). Tests replace `SecretStore` and `LanguageModels` with `test/fake-models.ts` (a scripted AI SDK v2 model).
- **Model keys (`libs/models`, `../docs/models.md` Keys):** `ModelKeysService` sets and removes provider keys: `/v1/organizations/{id}/model-keys` and, through `AgentModelKeysController` in `libs/agents` (which checks the agent exists), `…/agents/{agentId}/model-keys`; `GET` (`org:read` / `agent:read`), `PUT {apiKey}` and `DELETE …/{provider}` (`org:secret:write`). It writes the key to OpenBao (`SecretStore.write`, trimmed) and upserts a `model_keys` row (scope `organization` / `agent`, `scopeId`, provider, `hint`: the last four characters, `updatedBy`) in one transaction, so a failed write stores nothing (`503`). Lists come from the rows only; no key is ever returned.
- **Model catalogue (`libs/models`, `../docs/models.md` Models):** `ModelCatalogService` over `models` (provider, the provider's model ID, name, status `active` / `deprecated` / `retired`, context window, max output tokens, `version`) and `model_prices` (per million tokens: input, output, cache read, cache write, optional `longContext` rates above an input size; `effectiveFrom`; never updated). `/v1/models`: list (by name, `?status=`, `?provider=`, each with the price in force now), read, and prices (newest first) with any valid token (`@Authenticated`: the catalogue is the platform's); create (with its first price, `MODEL_ALREADY_EXISTS`), `PUT` (name, status, limits) and new prices (after the latest one, `MODEL_PRICE_INVALID`) only for platform services with `platform:manage` (`@PlatformAccess` alone: organization tokens are refused). New agent versions must name an `active` model (`assertAvailable`, `MODEL_NOT_AVAILABLE`); the gateway refuses a `retired` one (`ModelRetiredError`, failing the execution without retrying) and calls a model outside the catalogue (a version older than it) unpriced. The migration `ModelCatalogSeed` starts it with Anthropic's current models and prices; tests add `anthropic/claude` and a priced `scripted/scripted-model` in `test/global-setup.ts` (the catalogue isn't emptied between tests).
- **Budgets (`libs/models`, `../docs/models.md` Budgets):** `BudgetsService` over `budgets` (scope `organization` / `project` / `agent` / `task_tree`, its `scopeId`, `limitUsd` or none, `thresholdWindow`, `version`); what a scope spent isn't stored but summed from `model_calls` (`ModelGateway.spent`: per organization, project or agent, `agent_id`, since the start of the month in UTC, per task tree, `top_level_task_id`, over its life). `GET`/`PUT /v1/organizations/{id}/budget` (`org:read` / `org:manage`) and `…/projects/{projectId}/budget` (`project:read` / `project:manage`) in `BudgetsController`; an agent's, over all its projects, `GET`/`PUT …/agents/{agentId}/budget` (`agent:read` / `org:manage`) in `AgentBudgetController` (`libs/agents`, which checks the agent); a task tree's through any of its tasks, `GET`/`PUT …/tasks/{taskId}/budget` (`task:read` / `task:create`), and `budgetUsd` when creating a top-level task (`TaskBudgetsService` in `libs/tasks`, same transaction; `TASK_BUDGET_INVALID` on a subtask). `exceeded` names the narrowest budget that ran out (tree, then agent, then project, then organization); `afterCall` also publishes `budget.threshold-reached` at 80%, once per window. The runner checks before an execution starts (`ExecutionPreparer.assertBudget`) and the Mastra runtime after each model call (each step is metered by Mastra's stop condition, which it asks before reporting the step, or by `onStepFinish` for the last one; a run whose budget ran out stops before its next call, and one that ended on its own keeps its answer). `BudgetExceededError` → `ExecutionsService.pause`: the execution ends `paused`, its pending artifacts `partial`, the task `paused` with `pausedFor` (`task.paused`). Each round, `Housekeeping` runs deliveries and `PausedTasks.resume`: paused tasks whose budgets have room go back to `queued` (`task.resumed`, `reason: budget-available`).
- **Errors:** `DomainError` subclasses become `409` problem details with their `code`; add new codes to the spec's `DomainErrorCode` enum too.

### API contract

Spec-first: `../contracts/hephaestus.openapi.yaml`. `pnpm generate:api` runs `@hey-api/openapi-ts` (`openapi-ts.config.ts`) for Hephaestus's own types and Zod schemas (`libs/core/src/api/generated/`) and for a Polis HTTP client from `polis.openapi.yaml` (`libs/core/src/clients/polis/generated/`, exported as `PolisApi`), and `aether-asyncapi-types` for Polis's event payloads and Hephaestus's own (`libs/core/src/events/generated/`, exported as `PolisEvents` and, for its own, `HephaestusEvents` with `HEPHAESTUS_PUBLISHED_EVENTS`, and the commands it accepts, `HEPHAESTUS_COMMAND_TYPES`). All committed, formatted, never hand-edited (the generated client is excluded from lint); Iris generates its types from the Hephaestus spec. To change an endpoint: edit the spec, regenerate (here and in `../iris`), then update the DTO classes, mapper and controller.
