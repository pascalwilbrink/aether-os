# Engineering conventions

How every Aether-os service is built and run: databases, calls between services, configuration, logging and testing. HTTP API conventions are in `api.md`, events in `events.md`.

Status: agreed, documentation only. Sections marked **Proposal** are not agreed yet.

## Libraries

**Use NestJS libraries where one exists for the job**: the official `@nestjs/*` packages first, then established Nest integrations. They plug into Nest's dependency injection, lifecycle and testing (`Test.createTestingModule`, overriding providers), which a plain library wired by hand doesn't. Only where nothing fits, wrap the plain library in a small Nest module in Krepis, so services still consume it the Nest way.

| Need | Library |
|---|---|
| Configuration | `@nestjs/config`, validated with a Zod schema |
| Database | `@nestjs/typeorm` (already in use) |
| Transactions | `typeorm-transactional` (see Transactions) |
| Code generation from `contracts/` (types, Zod schemas, HTTP clients) | `@hey-api/openapi-ts` |
| Logging | `nest-winston` |
| RabbitMQ (topic exchanges, own queues, manual ack, headers), **only inside Krepis's messaging module** | `@golevelup/nestjs-rabbitmq` (rather than `@nestjs/microservices`, whose RMQ transport is built for request/response and fits our exchange-per-service model less well) |
| Health checks (`/health`) | `@nestjs/terminus` |
| Rate limiting (`429`) | `@nestjs/throttler`, with Redis storage when a service runs more than one instance |
| Scheduled work (outbox relay, retention, digests, budget windows) | `@nestjs/schedule` |
| Local events (everything services emit and handle; see Events in code) | `@nestjs/event-emitter` |
| DTOs, validation and serialization | **Zod**, with `nestjs-zod`: DTOs from `createZodDto`, the global `ZodValidationPipe`, and `ZodSerializerInterceptor` for responses (see DTOs and validation) |
| Testing | `@nestjs/testing` with Vitest (already in use) |

Deliberately **not** a Nest library:

- **OpenAPI:** specs are written first in `contracts/` (see `api.md`), so `@nestjs/swagger` isn't used to generate them.
- **HTTP clients:** generated by `@hey-api/openapi-ts` from the callee's spec (below), provided through a Krepis module rather than `@nestjs/axios`, so calls are type-checked against the contract.
- **Token verification:** `jose` (JWKS fetching and caching, JWT verification) inside Krepis's own guards; `@nestjs/jwt` doesn't verify against a remote JWKS, and Passport adds little for one token type.
- **OpenTelemetry:** the OpenTelemetry Node SDK with its auto-instrumentations (which include NestJS, HTTP, Express, Postgres, amqplib and Winston), started before Nest boots.
- **Pistis's OpenID Connect provider:** `oidc-provider`, mounted inside the Pistis Nest app.

## Service structure

Every service uses the same three layers: **controller → service → TypeORM repository**. This replaces the DDD / hexagonal layering (`domain/`, `application/`, `infrastructure/`, `presentation/`, repository ports) that Polis and Hephaestus use today.

```
HTTP request
   │  ZodValidationPipe → CreateProjectRequest (DTO)
   ▼
ProjectsController        routing, @RequirePermission, nothing else
   │  service.create(organizationId, dto)
   ▼
ProjectsService           business rules, transactions, events; uses ProjectMapper
   │  mapper.toEntity(dto, …) → ProjectEntity
   ▼
Repository<ProjectEntity> TypeORM, injected with @InjectRepository(ProjectEntity)
   │
   ▼
Postgres
   …and back: entity → mapper.toResponse(entity) → ProjectResponse (DTO) → ZodSerializerInterceptor
```

| Layer | Does | Doesn't |
|---|---|---|
| **Controller** | Routes, path and query parameters, `@RequirePermission`, `@ZodSerializerDto`; calls one service method and returns its result | Map, validate by hand, touch repositories, contain rules |
| **Service** | Business rules (state transitions, limits, tenancy checks), transactions, publishing events through the outbox; maps with its injected mapper | Know about HTTP (no `Request`, no status codes beyond Nest's exceptions) |
| **Mapper** | Converts DTO → entity and entity → DTO; an `@Injectable()` class per resource, injected into the service | Rules, I/O, repositories |
| **Repository** | TypeORM's `Repository<Entity>`, injected with `@InjectRepository(Entity)` (`@nestjs/typeorm`); custom queries as methods on a small `@Injectable()` class around it when needed | Rules |

Mapper shape:

```ts
@Injectable()
export class ProjectMapper {
  toEntity(dto: CreateProjectRequest, organizationId: string): ProjectEntity   // new entity, ID generated here (UUIDv7)
  applyTo(entity: ProjectEntity, dto: UpdateProjectRequest): ProjectEntity     // PUT: every editable field replaced
  toResponse(entity: ProjectEntity): ProjectResponse
}
```

Rules:

- **Services return response DTOs**, already mapped; controllers never map.
- **DTOs never reach the repository, entities never leave the service.** Only the mapper converts between them.
- **Entities are TypeORM entities** (`@Entity`), with no separate domain model. They hold no business logic beyond trivial derived values.
- **State machines are explicit:** where a resource has a lifecycle (task, agent version, artifact, organization), its allowed transitions live in one plain, pure module next to the service (e.g. `task-transitions.ts`), used by the service and unit-tested exhaustively. Invalid transitions throw a `DomainError` (→ `409`).
- **Services inject other services, never other repositories.** A service injects only its own repository; anything else (another resource in the same module, or another module) is reached through that resource's service. Repositories and entities are never exported from a module; its `index.ts` exports the module and its services.
- **At most 7 injected dependencies per class** (controllers, services, mappers, handlers alike). More is a sign the class does too much: split it by use case (e.g. `TaskReviewService` next to `TasksService`), or group dependencies that are always used together behind one service. It's a guideline, not a hard limit: an exception needs a reason in review.
- **Services never touch RabbitMQ.** They emit and handle local events (see Events in code).
- **External systems stay behind interfaces** injected into services: the Mastra runtime, the sandbox provisioner, `GitProvider`, `EmailSender`, `ModelGateway`, generated HTTP clients. Those are integrations, not persistence, and tests replace them with fakes; only the database is accessed directly through TypeORM.
- **IDs are generated in the mapper** (UUIDv7, from the `uuid` package) rather than by Postgres, so a new entity has its ID before it's saved (for events and `Location` headers).

Layout of a feature library:

```
libs/projects/src/
  projects.module.ts
  projects.controller.ts
  projects.service.ts
  project.entity.ts
  project.mapper.ts
  dto/                     createZodDto classes (one line each)
  index.ts                 public surface: the module and the service
```

## Transactions

**`typeorm-transactional`**, so services keep plain `@InjectRepository` repositories:

```ts
@Transactional()
async create(organizationId: string, dto: CreateProjectRequest): Promise<ProjectResponse> {
  const entity = await this.projects.save(this.mapper.toEntity(dto, organizationId));
  await this.events.emit('polis.project.created', { … });   // outbox row, same transaction
  return this.mapper.toResponse(entity);
}
```

- `initializeTransactionalContext()` runs in `main.ts` before Nest boots, and the `DataSource` is registered with `addTransactionalDataSource` in the TypeORM module setup; both are wrapped by Krepis so every service does it the same way.
- Every service method that writes is `@Transactional()`. Nested calls (a service calling another service's `@Transactional()` method) join the outer transaction by default (`Propagation.REQUIRED`), so a use case that spans services in one process commits or rolls back as a whole.
- The outbox listener writes through the same mechanism, so outbound events commit with the change (see Events in code).
- Work that must happen only after a successful commit (rare; normally a published event does the job) uses the library's `runOnTransactionCommit`.
- This replaces Krepis's `TransactionManager` / `TypeOrmTransactionManager`.
- Tests: integration tests run inside real transactions against Postgres; unit tests that call a `@Transactional()` method without a database use the library's test setup (or mock the decorator) so no `DataSource` is needed.

## DTOs and validation

**DTOs are generated from the OpenAPI specs as Zod schemas**, and validated with a `ZodValidationPipe`. class-validator and class-transformer go away.

```
contracts/polis.openapi.yaml
   │  pnpm generate:api
   ▼
libs/core/src/api/generated/zod.ts        // generated Zod schemas, one per spec schema
   │
   ▼
export class CreateProjectRequest extends createZodDto(zCreateProjectRequest) {}
   │                                       (nestjs-zod: a class Nest can inject, document and validate)
   ▼
@Post() create(@Body() body: CreateProjectRequest)   // validated by the global ZodValidationPipe
```

- **One source:** the spec. **`@hey-api/openapi-ts`** is the one generator for everything derived from a spec: TypeScript types, Zod schemas (its Zod plugin) and HTTP clients. It supports OpenAPI 3.1 and turns every schema into a Zod schema, carrying the spec's constraints (`format: uuid`, `minLength`, `pattern`, `enum`, `maximum`, …). Nothing is written twice, so the spec and the runtime validation can't drift, which `implements ApiSchema<'X'>` plus class-validator decorators couldn't guarantee.
- **Generated files are committed** and never edited by hand, like the generated types today.
- **DTO classes are one line:** `class X extends createZodDto(zX) {}` in the service's `presentation/http/`. They exist so Nest can use them as parameter types; all rules live in the schema.
- **Requests:** the global `ZodValidationPipe` (from `nestjs-zod`, registered once through Krepis) validates bodies, query and path parameters. Failures become `400 VALIDATION_FAILED` problem details with one `errors` entry per Zod issue, its `path` turned into a JSON Pointer (see `api.md`).
- **Responses:** `ZodSerializerInterceptor` with `@ZodSerializerDto(XResponse)` validates and strips every response against its schema, so a field that isn't in the spec never leaks (e.g. an internal column). A response that fails is a `500` and an error log: it's a bug, not a client error.
- **Strict objects:** request schemas reject unknown fields (`.strict()`), matching today's `forbidNonWhitelisted`; `PUT`'s "every editable field present, `null` to clear" (see `api.md`) falls out of the generated schema's `required` and `nullable`.
- **Types:** the generated TypeScript types and `z.infer<typeof zX>` describe the same schemas. `openapi-typescript` and `openapi-fetch` are replaced by `@hey-api/openapi-ts` everywhere, Iris included, which can also use the generated Zod schemas for form validation.
- **Conversion stays explicit:** Zod parses wire values (`string` timestamps, decimal strings for money); mapping to domain types (`Date`, branded IDs, decimals) happens in the DTO's `toDomain` / the response's `fromDomain`, not in the schema.
- **Beyond HTTP:** the same approach for event payloads (Zod schemas generated from the AsyncAPI specs, checked when publishing and when consuming) and for configuration (a Zod schema per service, used by `@nestjs/config`'s `validate`).

## Databases

- **One Postgres database per service**, owned by that service alone (`infra/postgres/init/`). No service reads or writes another's database, and there are no cross-database joins; data from other services arrives through their APIs or events.
- **TypeORM migrations**, staying with the ORM the services already use. `synchronize` is **off everywhere**, including local development, once a service is on Postgres: the schema only changes through migrations, which are generated, reviewed and committed like code.
- **Migrations run as a separate step** (`pnpm migration:run`), before the new version starts, never implicitly at application startup. Locally, `pnpm dev` runs them first. Migrations must be backwards compatible with the previous release (expand, then contract), so a rollback never needs a down migration.
- **Tenant columns on every tenant-scoped table:** `organization_id`, plus `project_id` where the data is project-scoped. Repositories always filter by them, and unique constraints include them (`UNIQUE (organization_id, slug)`).
- Later, as defence in depth: Postgres row-level security on `organization_id`, set per transaction from the request's token.
- **Column conventions:** `snake_case` names (a TypeORM naming strategy maps them from `camelCase`), `uuid` for IDs, `timestamptz` for times, `numeric(18,6)` for money, `jsonb` for free-form data. Enums as `text` with a check constraint, so adding a value is a cheap migration.
- **No soft deletes:** a deleted row is gone. Things with a history are archived through their status (see `api.md`).
- SQLite goes away entirely, in services and in tests.

## Events in code

Status: the **outbound** side is built (Krepis `EventsModule`: `DomainEvents.emit`, the outbox and the relay, with the trace context in AMQP headers; Polis publishes, with payload types generated from its AsyncAPI spec). The inbound side (consuming queues, the inbox, retries and dead-lettering) comes with the first consumer.

Services only know **local events** (`@nestjs/event-emitter`). RabbitMQ sits behind a messaging module in Krepis that bridges local events to and from the bus, so no service code imports or depends on RabbitMQ, and the transport could be replaced in one place.

```
Outbound (e.g. Polis)                                     Inbound (e.g. Hephaestus)

ProjectsService                                           Krepis messaging module
  │ emit('polis.project.created', event)                    │ consume from hephaestus.polis-events
  ▼   (inside the service's transaction)                    │ validate (Zod), deduplicate on eventId (inbox)
Outbox listener (Krepis)                                    ▼
  │ writes an outbox row, same transaction                emit('polis.project.created', event)  (local)
  ▼                                                         ▼
Outbox relay (Krepis)                                     @OnEvent('polis.project.created') in a service
  │ publishes to polis.events                               │ ack once the handlers succeeded,
  ▼                                                         ▼ otherwise retry → dead letter
RabbitMQ  ───────────────────────────────────────────────▶
```

Rules:

- **Local event names are the contract names, prefixed with the producing service**: Polis emits `polis.project.created`; Hephaestus, consuming it, handles the same name. A service sees one naming scheme for its own and other services' events.
- **Typed events:** every event is a class (or Zod-inferred type) generated from or checked against the AsyncAPI schema; services emit through a small typed wrapper in Krepis, not with free-form strings.
- **Not every local event is published.** Which local events go to RabbitMQ is explicit configuration of the messaging module (the service's AsyncAPI spec lists them). Others stay in-process.
- **Outbound goes through the outbox, always.** The outbox listener runs synchronously inside the emitting transaction, so the event is stored if and only if the change commits. The relay publishes afterwards (`@nestjs/schedule`), with the envelope fields (see `events.md`) and `traceparent`.
- **Inbound is idempotent:** the messaging module records each `eventId` it handled (an inbox table) and skips duplicates before emitting the local event. Handlers still shouldn't assume exactly-once.
- **Commands work the same way:** an incoming `task.create` becomes a local event handled by `TasksService`, the same service method the HTTP endpoint calls.
- **Local handlers in the same service** run inside the emitting transaction when they only change data in this service's database; anything that leaves the process (HTTP calls, email, provider APIs) happens in a handler of a published event or after commit, never inside the transaction.
- **Testing:** services are tested by asserting the local events they emit and by emitting local events at them; RabbitMQ only appears in the messaging module's own integration tests.

## Calls between services

- **Events by default.** A service that needs to react to another's change consumes its events (see `events.md`). A service that often needs another's data keeps its own copy, updated from events (e.g. Kerykes's copy of memberships).
- **Synchronous HTTP only** when the caller needs an answer to continue the current request (Hephaestus asking Proxenos for a repository token) or needs another service's current state to validate a write (Hephaestus checking that an agent version is published).
- **Generated clients:** generated by `@hey-api/openapi-ts` from the callee's spec in `contracts/`, so a call to a missing endpoint or with a wrong body doesn't compile, and responses can be validated with the same Zod schemas. No hand-written HTTP calls.
- **Identity:** a call carries the caller's own token, or one obtained by token exchange when acting for a principal (see `identity.md`). Never a forwarded user token to a service that didn't ask for one.
- **Timeouts and retries:** every call has a timeout (5 seconds by default). Retries with backoff only for idempotent requests: `GET`, `PUT`, `DELETE`, and `POST` with an `Idempotency-Key`. A wrapper in Krepis does this, so services don't each decide.
- **No chains or cycles:** a request should cause at most one synchronous hop to another service, and two services never call each other synchronously in both directions.
- **Trace context** travels on every call (`traceparent`), as the OpenTelemetry HTTP instrumentation does by default.

## Configuration and secrets

- **Environment variables**, read in one place per service and **validated at startup** with a Zod schema through `@nestjs/config`. A missing or invalid value stops the service with a clear message instead of failing on first use.
- Each service has a committed `.env.example` with every variable and safe local defaults; `.env` itself is gitignored (it already is).
- **No secrets in environment variables in production.** Each service authenticates to OpenBao (Kubernetes auth in production; a token for local development) and reads its own secrets at startup, renewing them while it runs. Database credentials: later, OpenBao's database secrets engine, so they're short-lived too.
- No feature flags in environment variables; settings that change behaviour per organization or project live in the owning service's data.

## Logging

- **Winston**, as the Nest logger (through `nest-winston`), configured once in Krepis: structured JSON to stdout, one object per line, with the redaction below applied as a Winston format. Services log through Nest's `Logger`, never by creating their own Winston instances.
- Every line carries `level`, `time`, `service`, `traceId`, `spanId`, and when known `organizationId`, `projectId`, `taskId` and the principal's `sub`. They're set once per request or message (from the token and the trace context), not by each log call.
- **Never logged:** secrets, tokens, `Authorization` and `Cookie` headers, prompts, completions, artifact content, email addresses. A redaction list in Krepis covers the known paths; anything content-like isn't logged at all. LLM content belongs in Langfuse, with its own redaction.
- Levels: `error` for something an operator must look at, `warn` for something unexpected that was handled, `info` for lifecycle events (started, task state changes), `debug` off in production.
- Logs leave through the OpenTelemetry Collector (OTLP logs), like traces, and are stored in **Grafana Loki**; Grafana shows them next to the traces from Jaeger (a log line links to its trace). OpenTelemetry's Winston instrumentation adds `traceId` / `spanId` to every log record and can send them over OTLP, so logs and traces link up.

## Testing

| Level | Covers | Runs against |
|---|---|---|
| Unit | Mappers, state transition modules, services' rules | Mocks or fakes of the repository and of external interfaces, an injectable clock |
| Integration | Services with their real repositories, migrations, the outbox, RabbitMQ consumers | Real Postgres and RabbitMQ in containers (Testcontainers), one per test run |
| End-to-end, per service | The HTTP API and message handlers, through the whole app | The same containers; other services replaced by fakes behind their generated clients |
| Contract | Every e2e response is validated against the service's OpenAPI spec, and every published or consumed message against its AsyncAPI schema | Automatically, inside the e2e and integration tests |

- **No SQLite in tests:** tests use the same Postgres version as production, so migrations, constraints and `uuid` / `timestamptz` / `jsonb` behave the same.
- **No cross-service end-to-end suite in CI** to start with; contract tests catch incompatible changes between services. Later: one smoke test of the full flow against `docker compose`.
- **No coverage target.** Domain rules and state machines (task lifecycle, approval, budgets) are tested exhaustively; glue code through the e2e tests.
- Tests are deterministic: an injectable clock, no real network, no sleeps (wait for conditions instead).
